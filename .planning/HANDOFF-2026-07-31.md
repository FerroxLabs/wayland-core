## 3. FIXES LANDED LOCALLY, NOT YET PUSHED

**`82455bd6` — macOS `$TMPDIR` intake (issue #937).**
`media_intake::open_once` walked every path component with
`O_DIRECTORY|O_NOFOLLOW`. On macOS `/var`, `/tmp` and `/etc` are OS-shipped
symlinks into `/private`, so the FIRST component of any temp path returned
ENOTDIR(20) and all six media/document surfaces refused every such path —
including a literal user-typed `/tmp/photo.png`. Ancestors are now canonicalised
once, after `validate_user_path` (order is load-bearing: canonicalising first
would collapse the `..` traversal the validator exists to refuse); the leaf is
deliberately NOT canonicalised, so leaf refusal is untouched.

Two tests asserted the old blanket-ancestor rule and are reversed on that half
deliberately (`media_intake`, `vision_tools`); the vision_tools test is also
renamed so its name doesn't outlive its behaviour.

**`df4602c6` — a containment defect, and the more serious of the two.**
`bash.rs` merged policy env into manifest env with a bare `extend`, so a
delegated-mutation shell carried BOTH the ambient host `TMPDIR` and the confined
`<scratch>/tmp`:
```
("TMPDIR", "/var/folders/8h/.../T/")          <- host temp
("TMPDIR", "/private/var/.../scratch/tmp")    <- confined
```
Duplicate env names resolve unpredictably in the child, so a shell restricted to
checkout+scratch could have written outside `fs_write_allow`. Policy names are
now stripped before its values are appended.

**Why only macOS saw it: Linux leaves `TMPDIR` unset,** so only the confined
entry existed and the test passed — for six runs — while the property it guards
was broken on the platform that does set it. Not a macOS bug; macOS was the only
place the instrument could see it.

`wcore-tools` on macOS: **1239/1239** (was 1230).

| E | session-journal reports two path representations for the same rejection | 5 | low severity |

### B + D — do these together, and read this before touching either

`crates/wcore-eval-scenarios/src/process_tree.rs`. The success path deliberately
leaves the child unreaped as a PID/PGID identity anchor (`WNOWAIT`), then calls
`group.kill()`. On Darwin that returns **EPERM**; `UnixProcessGroup::kill` (~L437-450)
tolerates only ESRCH, so **every clean shutdown fails its own cleanup**.

**DO NOT just add `|| EPERM` at L444.** There is a paired vacuity: on the same
platform `ProcessTree::terminate` (L218-235) sets `cleanup_complete = true` and
skips the containment-emptiness proof entirely, and `finish_cleanup` for
`Backend::ProcessGroup` is `Ok(())` (L325) — a gate with **no reachable fail
state**, while EPERM is a gate with **no reachable pass state**. Same file,
opposite failures, and `cleanup_verified` is still recorded as run evidence.
Blanket-tolerating EPERM converts a false failure into a false success.

Correct fix, both halves together, sharing one helper:
1. add `live_members()` — enumerate the group (macOS: sysctl
   `CTL_KERN, KERN_PROC, KERN_PROC_PGRP`; `wcore-sandbox` already wraps
   `macos_bsd_info`), counting entries whose `p_stat != SZOMB`;
2. in `kill()`, on EPERM return Ok **only if zero live members**; otherwise
   propagate — a live unsignallable process is a REAL containment failure;
3. implement the emptiness proof for `Backend::ProcessGroup` using the same
   helper and delete the `cleanup_complete = true` short-circuit.
   A `kill(-pgid, 0)` probe is NOT discriminating — signal-0 also returns EPERM
   in this state. Enumerate, don't probe.
4. Check the sibling implementation in `wcore-sandbox` before fixing one copy.

**D**: `crates/wcore-exec-backend/src/orphan.rs:321-333` uses a two-way
`cfg!(windows)` branch for a three-platform matrix; macOS silently inherits the
Linux arm. Make it three-way (BSD `etime` is `[[dd-]hh:]mm:ss`, convert to
seconds), or drop the subprocess on macOS for `proc_listallpids` +
`proc_pidinfo`. `the_real_process_table_passes_its_own_self_test_on_this_host`
already exists and is the test that caught it.

**C is a decision, not a fix.** The three `required_live_macos_*docker*` tests
have no reachable pass state on ANY host — proven on a Mac WITH Docker Desktop
running, so the "GitHub runners have no Docker" argument isn't even needed. They
also violate the repo's own live-gate pattern that `wcore-sandbox`'s equivalents
follow correctly (`#[ignore]` + env opt-in + skip-with-reason + a CI job
asserting the case executed).
