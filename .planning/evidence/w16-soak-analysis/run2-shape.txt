THIS FILE ADDS NOTHING NEW FROM THE PRODUCT. It is arithmetic over the 8938
per-cycle rows already in that receipt, done because c1 asks where the growth
lives and nobody had asked the data. Every number below is reproducible from
receipt.json alone.

1. THE GROWTH IS LINEAR IN CYCLE COUNT, not in wall time and not in load.
   Least-squares fit of quiescent_rss_bytes against cycle index:
       slope 417,726.7 bytes per cycle,  R^2 = 0.8432
   417 KiB retained per cycle, held after quiescence, 8938 times.
   Loadavg was 28.0 at start and 28.6 at end, so this is not a load artefact.

2. IT IS INDEPENDENT OF THE READER MODE. The matrix ran three reader profiles
   in near-equal thirds (fast 2979, disconnected 2981, slow 2978). Each one's
   own first-100 vs last-100, in bytes:

       fast          1,782,736,486  ->  6,540,927,263
       disconnected  1,686,625,894  ->  6,531,480,330
       slow          2,029,378,355  ->  6,560,249,487

   All three converge on the same ~6.53-6.56 GB. A leak in the streaming or
   slow-reader path would separate them; this does not. So the retention is NOT
   in the reader path, which is where a first guess would have gone.

3. ONE SESSION PER CYCLE, NEVER REUSED: 8938 distinct `session` values across
   8938 cycles. Combined with (1) and (2), the retained ~417 KiB is per-SESSION
   and survives the session's own teardown -- every cycle ends with
   delete_status 204 and get_after_delete_status 404, so the session is gone
   from the host's own view while its memory is not.

4. TIME-TO-FIRST-BYTE DEGRADES WITH IT, 28x. Mean headers_ms first-100 59.20 ->
   last-100 1663.83. Within each reader profile the same shape appears
   (~62 ms -> ~790-834 ms). That is the signature of a per-dispatch walk over a
   structure that grows with session count, and it is the user-visible cost of
   the same defect -- worth stating because the RSS number alone reads as
   "memory is cheap, ignore it".

5. ZERO CYCLE FAILURES. 0 of 8938 cycles have pass=false. The run did not fail
   on function; it failed on the frozen RSS bound alone.

WHAT THIS DOES NOT DO, and why c1 stays not-met:
   It narrows the search to per-session state that outlives session deletion,
   and it excludes the reader/streaming path. It does NOT name an allocation
   site or a retention path, and c1 explicitly requires a profile that
   reproduces the growth -- a code reading, or arithmetic like this, is not
   sufficient. The next instrument should be a heap profile over a short run
   with the session count as the independent variable, since 417 KiB/session at
   R^2 0.84 should reproduce in far fewer than 8938 cycles.
