WHAT ACTUALLY FAILS -- three distinct causes, all previously invisible
---------------------------------------------------------------------

(1) DISK ADMISSION -- 30/30 and 30/30, deterministic, not flaky at all

    dispatch floods: DispatchAdmission("dispatch requires 43486543872 bytes
    for 5 active workers, 0 bytes already reserved, and its safety margin,
    but only 30762147840 bytes are available")

    called `Result::unwrap()` on an `Err` value: DispatchAdmission("dispatch
    requires 34896609280 bytes for 4 active workers, 0 bytes already reserved,
    and its safety margin, but only 30762373120 bytes are available")

    The arithmetic, from crates/wcore-swarm/src/worktree.rs:125-127 and
    worktree_manager.rs:368-390:
        per transaction = min(MAX_TRANSACTION_WORKSPACE_BYTES = 8 GiB,
                              MAX_AGGREGATE_WORKSPACE_BYTES = 64 GiB / N)
        required        = per_transaction * N + existing + 512 MiB margin
    So 4 workers -> 32 GiB + 512 MiB = 34896609280 bytes exactly.
       5 workers -> 40 GiB + 512 MiB = 43486543872 bytes exactly.

    This is a FLAT 8 GiB-of-free-disk reservation per worker, taken up front,
    independent of what the worker will use. A 4-worker swarm refuses on any
    machine with under ~32.5 GiB free; a full 8-worker swarm needs ~64.5 GiB.
    It is fail-closed and the message is honest, but it makes `swarm dispatch`
    unreachable on an ordinary developer laptop and on every hosted CI runner.
    That is a product sizing decision that has never been stated anywhere a
    user would see it.

    NOTE ON SCOPE: this arm is conditional on free space, and it is why these
    two rows are 0/30 on WINH. It does NOT establish what happens on
    SEANDESKTOP, which has more disk. See "NOT MEASURED".

(2) WINDOWS SHARE VIOLATION DURING WORKSPACE ACCOUNTING -- nondeterministic

    worker process: sandbox child execution failed: workspace accounting:
    dispatch admission refused: workspace accounting refused ".git": io: The
    process cannot access the file because it is being used by another
    process. (os error 32)

    A transient ERROR_SHARING_VIOLATION on one file inside the workspace turns
    into a refusal of the whole dispatch. On Windows that is an everyday event
    (git's own handles, the indexer, AV). An accounting walk that cannot open
    one entry has not proven the workspace is oversized; it has proven it could
    not look.

(3) DESCENDANT STILL HOLDS THE RETAINED CHECKOUT DESCRIPTOR -- nondeterministic

    worker descendant still holds the retained checkout descriptor;
    transaction quarantined and its reservation held for retry

    Hit by BOTH `malformed_heartbeat_*` and `public_dispatch_owns_git_authority_*`.
    The loan check (`checkout_loan_outstanding`, dispatch.rs) runs before the
    Windows kernel has finished closing the reaped job's inherited handles, so
    the loan counter is still non-zero. Each occurrence quarantines the
    transaction AND HOLDS ITS RESERVATION -- against the 8 GiB-per-worker
    budget in (1), a machine that hits this repeatedly loses dispatch capacity
    until something reclaims it.


NOT MEASURED -- stated plainly rather than papered over
-------------------------------------------------------
The self-hosted SEANDESKTOP leg of run 30727452188 was still `queued` after
~50 minutes and never started. Both Windows runners were `busy=true` the whole
time and the account had 25-37 runs queued. Direct ssh to the same box was
attempted four times (120s, 300s, 900s, 600s) and returned rc=124 every time:
the session authenticates, the exec request is accepted, and no output ever
comes back.

So: the six tests have been re-measured on Linux and on a hosted Windows server
SKU. They have NOT been re-measured on the exact box that produced the original
FLAKY reports. `windows-flake-ledger.yml` is on the branch and its self-hosted
job will publish `windows-flake-ledger-<run_id>` whenever the runner frees up.
