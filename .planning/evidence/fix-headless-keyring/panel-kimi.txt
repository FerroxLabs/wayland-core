• **1. Degrade vs. refuse**

  Degrade is right — refuse-to-start solves the wrong problem. On a headless Linux host with no keyring, crash recovery was never deliverable; the operator isn't losing a property they could have had, they're being told a default they never configured can't run there. Refusing to start would make the default configuration (durable sessions ON) a guaranteed outage on an entire, common host class — the cure becomes worse than the bug you're fixing (a server that accepts work, reports Healthy, and answers nothing is the actual fail-silent disaster here).

  Two hardening conditions, though:

  - The health endpoint/command must report the degraded state ("durable sessions: DISABLED — no keyring"), not just Healthy. A stderr line scrolls away; health is what operators and load balancers actually watch. The current bug *was* a health lie — don't ship a fix that keeps a smaller version of it.
  - Distinguish default-on from explicitly-configured-on. If the operator wrote `durable_sessions = true` in config and it silently turns off, that *is* overriding an explicit choice. Explicit opt-in that's unachievable deserves a louder refusal (fail startup, or require an `allow_no_keyring = true` ack); the silent degrade should apply only to the default path.

  **2. Security property**

  None weakened — it improves slightly. The journal encryption protects one thing: provider requests at rest. With no journal, no provider request ever touches disk, so there is nothing at rest to protect. Same for history: if it was encrypted under the same key, disabling durable sessions removes that at-rest confidential surface entirely. You cannot leak what you never persist. Confidentiality is monotonically better in the degraded mode.

  What you actually lose is **availability** (crash recovery of an in-flight turn) and an audit/forensics trail — neither is a confidentiality property the encryption was guarding. One caveat: with history off, an interrupted turn's context is gone rather than recoverable, so retries must be idempotent or client-driven — that's a correctness concern for callers, not a security one.
