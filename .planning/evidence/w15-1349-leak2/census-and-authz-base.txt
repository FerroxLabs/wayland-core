  IT IS NOT A MISSED TRIM, and this part is a code reading, stated as one.
  crates/wcore-cli/src/acp_engine/lifecycle.rs:291 is the only caller of
  wcore_config::allocator::release_idle_memory: it runs when the LAST session

  pages nobody asked it to return. No build was spent testing a "trim more
  often" variant, because this reading says it could not move the sample.

  soak's 32 MiB growth limit. Over 640 cycles it shows no sign of saturating.

  arm                        binary  conc  payload  durability  pass   relay-cancelled
  relay-base-c8-optional     base      8   16 MiB   optional     2/16       14
  relay-fix-c8-optional      fix       8   16 MiB   optional     0/16       16
  relay-fix-c32-durable-1m   fix      32    1 MiB   on          32/32        0

  * PRESENT ON THE BASE. The cancellation is the ACP relay's per-turn bound
    (crates/wcore-cli/src/acp_engine.rs, `protocol_channel`), which this change
    does not touch; the base binary hits it too. The fix is marginally worse
    (0 vs 2 of 16), consistent with it now letting all eight turns reach the
    relay at once instead of holding some behind five-second key timeouts.
  * NOT A CONCURRENCY LIMIT AS SUCH: 32 concurrent 1 MiB turns all pass, and
    16 MiB at concurrency 1 passes. It is eight fast 16 MiB readers at once,
    all served from ONE Python client process.
  * WHY THE ORIGINAL SOAK NEVER SAW IT: its source 3530199fb is NOT an ancestor
    of this release base 38f82b87f -- it sits on a different line with its own
    copy of the guard -- and there 967 fast 16 MiB rows at concurrency 8/32
    passed with 0 relay cancellations in 8,938 cycles. On this line
    crates/wcore-cli/src/acp_engine.rs has one commit since the fork, 1780b3164.
  * NOT ESTABLISHED: whether the soak's own schedule trips it. The soak has at
    most one fast 16 MiB reader per concurrency-8 batch and ~3 per
    concurrency-32 batch, far less client-side contention than eight at once.
    The soak asserts every row of every batch, so if it does trip, the soak
    aborts within its first few dozen batches rather than after two hours --
    which makes launching it the cheap way to find out.

THE A/B VERDICT. Every mode in which the store must refuse refuses on the fix
exactly as on the base -- 0 turns served out of 123 in each, at concurrency 1, 8
and 32. The single difference is the one the repair is for: a HEALTHY vault
under concurrency goes from 5/123 served to 123/123. On the fix, every refusal
after corruption carries the store's own "secure recovery storage could not be
read" -- none is a timeout -- because loads no longer queue behind each other,
so the refusal the operator reads is now the true cause every time.

the key from the healthy vault first, the vault was overwritten at a quiescent
point, and not one of the 123 later sessions -- including 32 concurrent ones --
was answered with the key those earlier sessions had loaded.
