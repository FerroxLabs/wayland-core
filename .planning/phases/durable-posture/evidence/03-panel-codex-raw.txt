## Measured facts (all verified in the source at HEAD; treat as given)

1. Durable sessions write a per-session append-only journal at
   `$WAYLAND_HOME/sessions/<id>.journal`. The FILE is created mode 0600 inside a 0700 directory,
   and the reader REFUSES to open it if `mode & 0o077 != 0` or the owner uid differs. So the
   journal at rest is already an owner-only file, enforced.

2. The journal body is NOT encrypted. It is JSONL metadata: event types, cursors, digests,
   checkpoint records. Prompt/response CONTENT is deliberately excluded — a test asserts the
   prompt bytes do not appear in the journal.

3. Exactly ONE field needs a secret key: `sealed_prepared_request`, the exact prepared provider
   request (which does contain the full conversation), sealed with XChaCha20-Poly1305 under a
   32-byte key. That key is stored in the "confidential credentials store".

4. The confidential store has exactly two candidate backends: the OS keyring, or an
   Argon2id-encrypted vault file. The vault is considered AVAILABLE only if the operator supplied
   a passphrase out-of-band (`WAYLAND_VAULT_PASSPHRASE` or `..._FD`). There is no third candidate.

5. Consequence, and the thing under review: on a headless Linux server with no OS keyring and no
   passphrase (the normal state), neither candidate is available, so a fix that shipped today
   turns durable sessions OFF ENTIRELY for the whole process. No journal, no session directory,
   nothing on disk. The turn runs. A one-time notice is printed to stderr at startup.

6. Before that fix, the product REFUSED: it returned a non-retryable `engine_error`, never called
   the provider, and never started a turn — but it DID still write the journal file recording the
   refusal.

7. A `ProviderDispatch` recovery checkpoint currently REQUIRES `sealed_prepared_request` to be
   present; a checkpoint without it is rejected as an invalid transition.

8. Measured just now: in the degraded (no-journal) mode, the `ready` frame emitted to a
   `--json-stream` host contains NO `session_id` field at all. The host is told nothing else. A
   daemon that started three weeks ago has told nobody anything since.

## The argument that motivates changing this

The retry after a crash does not come from the engine. It comes from the messaging platform
redelivering an inbound, or an operator retrying, or a human resending because they got no reply.
With NO record on disk, nobody can determine whether the prior effect (the provider call, a tool
execution, an outbound send) already happened. The absence of a journal does not remove the
ambiguity; it exports the ambiguity to the user. So "no secure store therefore no journal" looks
like a false dichotomy: the right move may be to degrade the ENCRYPTION, not the JOURNALING.

## The four options. Pick one (or argue a fifth).

**A. Auto-provision a machine-local key.** When there is no keyring and no passphrase, generate a
random 32-byte key and store it in a 0600 file in the SAME 0700 profile directory as the journal.
Journaling continues unchanged. No operator action, no config.

**B. A, but policy-gated.** Same mechanism, but only when the operator opts in
(`[session] degraded_durability = "machine_local_key"`). Default is fail-closed: refuse to start
a turn, as in fact 6.

**C. Status quo.** Keep the amnesia degrade.

**D. Journal without the seal.** In degraded mode, write the journal but OMIT the sealed prepared
request. Introduce an explicitly unrecoverable dispatch record: "a provider call with request
digest X was dispatched at T; outcome unknown; this turn CANNOT be replayed." No new key at rest
exists at all. Recovery downgrades from "resume the turn" to "tell the operator, truthfully, that
the effect is unknowable and require a decision." Costs a journal schema change (fact 7).

The framing conflates four separate properties: auditability, confidentiality, crash recovery, and exactly-once effects. The correct invariant is: **no external effect may occur unless a durable intent record exists first**. Failure to encrypt a replay payload may reduce recovery capability; it must not disable the audit trail.

1. A colocated 0600 key provides only a narrow, real property.

It protects against selective exfiltration where the attacker obtains the journal but not the rest of the profile:

- A backup/export containing only `sessions/`
- A mistakenly uploaded journal
- A path-scoped collector
- A snapshot or archive that excludes the key

It does not protect against:

- Another local user: journal permissions already stop them.
- A process running as the owner: it can read both.
- Root: it can read both.
- Whole-profile backups: both are copied.
- A disk image: both are present.
- Machine compromise while Wayland runs: both are accessible.

So it is not pure theatre, but presenting it as a “confidential credentials store” would be dishonest. It is defense against partial disclosure, not meaningful machine-at-rest separation. A realistic disaster-recovery backup probably copies the whole profile, making the protection vanish precisely where operators may expect it to matter.

That narrow benefit may justify an optional machine-local recovery key. It does not justify silently treating one as equivalent to a keyring or passphrase-backed vault.

2. Choose D as the default.

C is indefensible. It turns loss of a confidentiality facility into loss of the audit trail, despite the audit metadata already being owner-protected and deliberately content-free.

B is also wrong as written. Fail-closed-by-default recreates the keyring-less Linux release blocker. It preserves security by making the product unusable.

A preserves the strongest recovery capability, but silently downgrades the key’s security class. It also introduces key lifecycle, backup, rotation, deletion, and continuity problems. If the fallback key disappears, prior sealed checkpoints become unreadable anyway.

D preserves the essential operational invariant without introducing a pretend secure store:

- Journal metadata continues.
- External effects remain auditable.
- Conversation content is not newly persisted without an approved secret store.
- Recovery truthfully reports that automatic replay is unavailable.

I would make D the default and optionally offer A as an explicit enhancement for operators who prefer autonomous recovery over stronger content-at-rest separation. That is not B: lack of opt-in must mean metadata-only durability, not refusal.

D also requires two non-negotiable changes:

- If the journal cannot be appended and durably flushed, external execution must fail closed.
- The JSON `ready` frame must disclose something like `journal=metadata_only`, `sealed_recovery=false`, and `replay=operator_required`. A one-time stderr notice is not an API contract, especially for a three-week-old daemon.

3. C is the downgrade-abuse vulnerability.

Under C, disrupting D-Bus or removing the vault-passphrase source strips the audit trail while leaving execution enabled. That is a direct security downgrade: “disable credentials backend” becomes “obtain unrecorded execution.”

A does not inherently permit unrecorded execution. It substitutes a local key and continues journaling. It does, however, let the attacker downgrade confidentiality and potentially split key continuity. The implementation must never generate a fresh fallback key and silently treat an existing session as recoverable under it.

D also does not permit unrecorded execution, provided journaling is mandatory before every effect. It permits an attacker to degrade automated recovery, but not to erase the evidence that execution may have occurred.

Strictly, B best denies unrecorded execution because it denies all execution. Among usable designs, D is stronger than A because auditability no longer depends on any secret backend or fallback-key provisioning path.

The ordering must be write-ahead:

1. Append and flush an effect-intent record.
2. Attempt the provider, tool, or outbound operation.
3. Append an acknowledgement or result record.

A crash between steps 1 and 3 means “possibly effected,” not “nothing happened.”

4. The existence of any old journal must not brick the whole process. Automatic continuation of an affected session is a different matter.

The case for refusal is strong when the selected session has a sealed checkpoint that is required to reconstruct its state:

- Continuing under the same session identity would falsely claim causal continuity.
- The previous call may be in flight or may have completed.
- Starting from reconstructed-but-incomplete state risks duplicate effects.
- Generating a new key does not restore the missing history.

Therefore, the product must refuse to automatically resume or silently fork that session.

The case against global refusal is equally strong:

- The keyring outage may be temporary.
- Unrelated new sessions do not depend on the old sealed request.
- One abandoned historical session should not become a permanent denial-of-service primitive.
- Readable journal metadata may still prove that the session reached a safe terminal state.

The correct policy is state-sensitive:

- If the journal proves a clean terminal checkpoint and no sealed state is needed, continuation may be allowed in declared metadata-only mode.
- If an in-flight or recovery-required checkpoint exists, mark that session locked and require the key or an explicit operator decision.
- Permit a genuinely new session, using a new identity and an explicit `forked_from_locked_session` relationship when applicable.
- Never silently reuse the old session ID or pretend the fork is a resume.
- Surface the condition through the JSON protocol, not only stderr.

So: no global process brick, but no automatic continuation from unknowable state.

5. D is worse than A for recovery, but better than C for ambiguity management. It does not prove that an external effect happened.

A local record cannot atomically prove a remote effect:

- Written before the call, it proves intent, but the call may never have occurred.
- Written after the call, a crash can occur after the remote effect but before the record.
- Even “socket write succeeded” does not prove the provider accepted or executed the request.

The honest state is therefore: **this effect may have been attempted and may have occurred**.

A request digest alone is insufficient unless it is bound to stable correlation data. D should record at least:

- Stable inbound delivery/message ID
- Logical turn and effect ID
- Session ID and journal epoch
- Effect type and destination
- Prepared-request digest
- Intent timestamp and attempt state
- Provider idempotency key, when supported
- Provider receipt/result ID, when obtained

This must cover tool executions and outbound sends, not merely provider dispatch.

With those identifiers, D is sufficient to prevent a blind replay and to tell the operator which redelivery conflicts with a possibly completed effect. It is not sufficient to determine whether the remote effect actually occurred. That requires a provider/platform receipt lookup, an idempotency mechanism, or human adjudication.

A’s seal is genuinely better for reconstructing the exact request and retrying it consistently. But the seal alone still does not provide exactly-once execution. D is preferable as the mandatory baseline because it preserves truthful evidence without persisting recoverable conversation content under a weakly separated key.
