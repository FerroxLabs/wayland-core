<objective>
Complete the governed plugin lifecycle and prove Success Criterion 3: a plugin can be scaffolded, tested, signed, installed, approved, inspected, updated, rolled back, removed, published, recovered and compatibility-checked — every one of them driven through the real `wayland-core` CLI.

Purpose: OpenClaw is ahead of Wayland on plugin and app product completeness, and this is the criterion that closes it. Wayland already has the hard half — a real Ed25519 verification path, quarantine, a lockfile, a marketplace resolver, a scoped registry API and a build-time isolation lint. What it does not have is the operator lifecycle around them: today `wayland-core plugin` offers install, list, available, remove and three marketplace verbs, and nothing else. A plugin author cannot scaffold, cannot sign, cannot publish; an operator cannot inspect, approve, update, roll back or recover.
Output: the missing verbs implemented on top of the existing primitives, retained generations that make update/rollback/recover real, a binary-driving regression suite, and a captured transcript of all twelve verbs run against the shipped binary on Linux and Windows.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| marketplace/registry → install root | Third-party plugin bytes cross into a directory the agent will load code from |
| plugin bundle → signature verification | Attacker-supplied content meets the Ed25519 trust root |
| install root → agent loader | Installed content becomes executing code inside the agent process |
| operator → approval record | A human decision becomes durable authority that later loads depend on |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-25-02-01 | Elevation of privilege | `plugin approve` / `plugins/loader.rs` | critical | mitigate | Approval is a load-time GATE, not a prompt: the loader refuses to initialise an unapproved plugin, and the negative case is the plan's most important test |
| T-25-02-02 | Tampering | `plugin install` of a mutated bundle | critical | mitigate | Content digest plus detached Ed25519 signature verified against the existing pinned trust root before install commits; a single mutated byte is rejected |
| T-25-02-03 | Elevation of privilege | approval surviving an update | high | mitigate | Approval is bound to the content digest, so updating a plugin invalidates the prior approval instead of inheriting it |
| T-25-02-04 | Spoofing | a second signing scheme | high | mitigate | Signing reuses `self_update.rs`'s pinned-key pattern and `sig_verifier.rs`; minting a second trust root is termination state 3, not an implementation choice |
| T-25-02-05 | Tampering | `plugin recover` resurrecting quarantined content | high | mitigate | Recovery is explicitly forbidden from restoring quarantined content or a revoked approval, and that is a tested behavior |
| T-25-02-06 | Denial of service | interrupted update destroying the installed plugin | high | mitigate | Plan-then-commit over retained generations, so an interrupted update leaves the prior generation live; proven by killing an update partway |
| T-25-02-07 | Repudiation | a verb implemented as a success-printing stub | high | mitigate | Every verb's proof is an independently observed STATE CHANGE, never the printed line |
| T-25-02-08 | Information disclosure | signing key handling | medium | mitigate | Key path supplied by the operator, never copied into the install root, the bundle or the transcript |
