You are auditing a security design decision in a Rust AI-agent CLI (wayland-core). Answer decisively.

CONTEXT
- The agent loads "on-disk plugins": each is a directory under a plugins root (e.g. ~/.wayland/plugins/<name>/plugin.toml). A loader walks the root, and for each manifest may spawn a subprocess, compile a WASM component, or register declarative hooks/MCP servers. Existing controls: per-root path-prefix containment, symlink refusal, and (for plugins that declare an entry binary) detached Ed25519 signature verification against a trust-anchor directory.
- We are ADDING an operator "approval" gate so an installed-but-unapproved plugin cannot execute. Approval is durable state recorded in the plugins root (approvals.json), bound to the SHA-256 content digest of the plugin directory, so updating a plugin invalidates its prior approval.
- Constraint: thousands of existing installs already have plugin directories in that root that were never "approved" (the concept did not exist). Existing integration tests also drop plugin dirs into a temp root and expect them to load.

THE QUESTION: what should the enforcement default be? Pick exactly one.

A) ROOT-SCOPED GOVERNANCE. A plugins root becomes "governed" the moment the new lifecycle writes its state file (generations.json) into it — i.e. as soon as the operator installs or approves anything through the new verbs. Inside a governed root, EVERY plugin directory must carry an approval record matching its current content digest or the loader refuses it. A root with no governance state behaves exactly as today (no approval required). Consequence: an operator who uses the new lifecycle once implicitly puts pre-existing sibling plugins behind the gate, and they stop loading until approved.

B) PER-PLUGIN GOVERNANCE. Only plugins that were installed through the new lifecycle (i.e. that have a generation record) require approval. A plugin directory with no generation record loads as today. Consequence: an attacker who simply writes a plugin directory into the root, bypassing the installer, is not subject to the approval gate at all.

C) GLOBAL ENFORCEMENT WITH CONFIG OPT-OUT. Every on-disk plugin requires approval, always, with a config flag (default ON) to disable. Consequence: existing installs and existing tests break on upgrade until each plugin is approved.

D) GLOBAL ENFORCEMENT, DEFAULT OFF, config flag to turn on. Consequence: the gate is advisory unless the operator opts in.

Judge on: does the option actually close the threat (unapproved code executing inside the agent), can the gate genuinely fail (not self-passing), and is the migration honest rather than silently fail-open?
