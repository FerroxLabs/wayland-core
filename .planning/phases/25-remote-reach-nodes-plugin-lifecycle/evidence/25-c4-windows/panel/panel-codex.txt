A security lane must prove an egress-denial control on Windows. The Linux proof used a VALID cloud API token against a nonexistent app, and the positive-control arm showed the product reporting `machine listing returned HTTP 404: {"error":"app not found"}` from api.machines.dev (Fly.io). On Windows no valid token exists and none may be moved there, so the lane used a deliberately invalid placeholder token; the code only rejects an EMPTY token, so the HTTP request is still made and the product reported `machine listing returned HTTP 401: {"error":"Authenticate: token validation error"}`. The deny arm, differing only by one config key (egress_allow), reported `egress denied ... blocked by the security policy`. A third leg with the PRE-FIX binary and the SAME deny config still got the 401, proving the gate can fail. Question: is the 401-from-invalid-token positive control evidentially EQUIVALENT to the 404-from-valid-token one for the specific claim "the request physically left the machine and a remote server answered", or is it materially weaker? Answer with a one-line verdict of EQUIVALENT or WEAKER, then at most 5 lines of reasoning naming any way a 401 could be produced WITHOUT the packet leaving the host.
