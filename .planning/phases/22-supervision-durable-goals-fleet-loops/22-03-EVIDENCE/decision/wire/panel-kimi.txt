  REASONING=Condition 1's binding text scopes the mandate to "every AUTHORITATIVE effect path," and F1 establishes that `retained_worker_count` is not an effect path at all — it writes nothing, so there is no commit for a fence to guard and the decision record's "reservation accounting write" label is factually wrong against the verified code. The read is evaluated fresh at dispatch time by the dispatcher itself, not replayed by a task owner holding a stale epoch, so the failure mode fencing exists to kill (superseded owner commits a duplicate effect) has no actor here — F3 removes the worker as an attacker and F2 removes any owner-mediated path to the read. F4 closes the residual worry: the resource being counted is fenced by a kernel flock lease, and the miscount direction for a live-but-superseded owner is over-counting, which fails closed (fewer admissions), not open. The one real defect I can find — cross-process over-admission — is not addressed by route (a) or (b) anyway: an epoch comparison at the ledger does not serialize two parents' `read_dir` calls, so C's prescribed remedy does not fix C's only candidate hazard; that hazard wants a cross-process admission flock, which is a different mechanism belonging to a different condition. Since the code is a read, is unreachable by owners, and is conservatively wrong when wrong, it satisfies Condition 1's own exemption logic by the same reduction-by-removal already accepted for the heartbeat path — except more cleanly, because here nothing even needs the "cannot affect" showing; it is simply not a write.
  ATTACK=The strongest argument against A: Condition 1 names this file and line verbatim and explicitly denies the exemption to it, so picking A overrides the letter of a binding decision record on the strength of a re-derivation, and if the panel's re-derivation is wrong anywhere (e.g., some future caller of `DispatchLimits::admit` treats the count as authoritative for reassignment), the fence has been silently half-closed — precisely the failure mode the condition's final sentence warns about. The safe answer to that is not B's perpetual review-limbo but to amend the decision record with the F1/F4 evidence so the closure is documented rather than asserted.
  CROSS_PROCESS=Yes, there is a real hazard: two parents in different OS processes both pass their per-process `dispatch_gate`, both `read_dir` before either finishes reclaiming/admitting, and both can admit against a stale `retained`, so total retained worktrees can exceed `MAX_RETAINED_WORKTREES` by up to roughly one parent's worth of admissions. But the consequence is bounded disk-retention overshoot — not a duplicate ledger effect and not a lost completion, since actual effects remain fenced by `TaskAuthority` and the reducer — and routing this read through a claim-epoch check would not prevent it, because epoch fencing serializes task ownership, not parent admission; the correct fix is a cross-process `flock` on an admission/serialization file in `CONTROL_DIR`, which should be filed as its own finding rather than holding Condition 1 open.
