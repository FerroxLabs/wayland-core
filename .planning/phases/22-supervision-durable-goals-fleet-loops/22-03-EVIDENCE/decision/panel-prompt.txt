=== THE QUESTION (verbatim) ===
What revokes a claim held by a worker that may be dead, and what refuses that
worker's late write if it was merely slow?

=== CONTEXT ===
A "Fleet" fans work out to N parallel workers, each in its own git worktree. We
are adding a durable task ledger so claims and dependencies survive
kill/restart/reassignment WITHOUT duplicate execution or lost completion. A claim
held by a process that has died looks exactly like a claim held by a process that
is wedged. Every revocation scheme trades a duplicate-execution window against a
stall. The second half of the question determines whether the requirement can be
met at all: a revocation with no fencing has an unbounded duplicate-execution
window regardless of how short its lease is.

=== THE FOUR OPTIONS (verbatim, in rotated order) ===

[id: heartbeat-liveness]
NAME: Heartbeat with a missed-beat threshold: an owner that stops beating loses its claim
PROS: Detects a wedged owner that a lease alone would keep waiting for; cheap to
observe; maps naturally onto the existing worker status surface
CONS: Answers the revocation question but NOT the fencing question, so a
wedged-then-recovered owner can still land a late write; on a suspended machine
every worker misses every beat and the whole fleet reassigns at once; needs a
fencing mechanism beside it to meet the criterion

[id: escalate]
NAME: Escalate - the measured baseline shows the criterion cannot be met without a mechanism outside this plan's scope
PROS: Refuses to ship a claim model whose duplicate-execution window is unbounded
but unstated; keeps the gap visible
CONS: Success Criterion 2 stays open

[id: os-process-liveness]
NAME: Probe the operating system for the owning process rather than inferring liveness
PROS: Highest-confidence liveness signal available and it does not depend on the
owner cooperating; on Windows the job-object containment already established by
earlier work makes descendant liveness observable rather than guessed
CONS: Only valid when the owner is a local process - it does not generalize to a
reassignment across hosts, which later phases will want; process-identifier reuse
makes a naive probe unsafe and it needs a start-time or handle binding to be
sound; still answers only the revocation half

[id: lease-with-fencing-token]
NAME: Time-bounded lease plus a monotonic fencing token: a superseded owner's write is refused because its token is stale
PROS: The only option that bounds duplicate EFFECT rather than merely duplicate
execution, which is what the requirement actually asks for; the token is a small
durable value that fits the Task record; it degrades correctly when a clock jumps
or a machine is suspended, because the refusal is ordering-based rather than
time-based
CONS: Every effect-producing write path must present its token, so the fencing
surface is wider than a lease alone; a path that forgets to present it is a
silent hole and needs a structural guard rather than review discipline

=== MEASUREMENT 3: SUSPEND BEHAVIOR (live, Linux) ===
SUSPEND-CLOCK: stopped_s=12 observed_advance_s=12 missed_beats=12 catchup_beats=12
The monotonic clock advances THROUGH an OS-level stop, so a time-based lease held
by a stopped worker expires on schedule; and a heartbeat scheme misses every beat
(12 of 12), so any threshold below 12 reassigns the whole fleet at once. An
ordering-based refusal is unaffected by either.

=== WHAT YOU ARE DECIDING ===
Pick the claim-revocation model to implement. Weigh especially: (a) the Linux
baseline shows the kill reaps the tree, which weakens the "superseded owner still
running" worry ON LINUX specifically; (b) the Windows kill behavior is UNMEASURED,
so any argument that relies on descendants always dying is Linux-only; (c) two of
six enumerated fence paths cannot be structurally guarded today.
