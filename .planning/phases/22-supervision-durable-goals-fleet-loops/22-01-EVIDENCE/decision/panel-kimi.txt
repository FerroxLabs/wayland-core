• ## 1. Which option should be authorized

  **additive-at-current-version.** The decision turns on whether a migration is *needed*, and the evidence answers that directly rather than by argument. M1 shows that growing `SessionEvent` changes nothing about decoding or reducing existing frames — the pre- and post-change reductions of a real 84KB journal are byte-identical (same SHA256). M2 shows the post-change binary can write a new-variant frame at v5 and the only delta in the re-reduction is the chain head (`last_seq`, `last_checksum`), which is exactly what a correct append should touch. M0 supplies the structural guarantee that makes this safe rather than accidental: the reducer's `apply_event` match is exhaustive with no wildcard, so no new durable record can enter the enum without a deliberate reduction decision — the "silent rewrite of accepted behavior" that the phase forbids is compile-time impossible. And the source itself settles the design intent: the in-source note at `session_journal.rs:2190` says the frozen list is "Frozen at the v4 boundary. New event variants belong to v5+", and `enforce_event_schema_boundary` applies its 49-name allow-list only to frames declaring v4. Adding Goal/Task/Wait variants at v5 is not working around the boundary machinery; it is using the boundary exactly as the accepted F12 code documents it. A version bump would force every existing journal through a migration whose only justification would be ceremony — the migration probe shows the cost is bounded (3 reds in 76 tests), but bounded cost is still cost with zero correctness benefit, and each migration subject is a new opportunity to get the re-frozen legacy list wrong, which the option's own cons admit is a silent-failure mode.

  On non-revertibility: the concern is legitimate but it is precisely what Task 1 measured. The catastrophic form of a wrong additive choice is a forward-incompatible read that silently truncates — M3 measured that this does *not* happen: the pre-change binary fails closed (exit 3, zero bytes on stdout, explicit error naming the unknown variant). So the worst case of the additive option is a documented hard refusal on downgrade, not corrupt state. M4 closes the snapshot/authority side of the same question. The residual obligation is the cons paragraph's own: document the downgrade behavior and accept that "has Goal records" must be asked of journal content, not inferred from the version number. Escalation is not warranted — nothing in the measurements shows accepted F12 behavior being invalidated; quite the opposite, replay equality was proven cross-binary with hashes.

  ## 2. Is Task 1's verdict sound

  **Yes, with both limitations stated and neither overturning it.** Limitation (a) — no `tool_execution_*` frames in the corpus because of the 401 — does not weaken the compatibility claim, because the claim is not about any particular event type's content. It is about three mechanisms: serde decode of the internally-tagged enum, exhaustive reduction, and the version-gated boundary check. Those mechanisms are variant-agnostic; M0 proves the reducer cannot special-case or skip an unknown arm, and M1/M2 were measured over a corpus spanning 9 real event types including the full turn, provider-attempt, budget-authority, and checkpoint lifecycle. A `tool_execution_committed` frame would exercise the same decode-and-reduce path the probe variant already exercised. It would have been *nice* corroboration, not missing load-bearing evidence. The 401 is also honestly disclosed with its cause, which is what the evidence standard requires.

  Limitation (b) deserves a more careful split. The Windows leg matters where the platform actually differs: the writer lease, where byte-range locking is mandatory rather than advisory and is a recorded prior defect class. But the question COMPATIBLE-AT-V5 answers is a *schema* question — does adding variants at v5 preserve decode and replay of existing journals — and that logic is platform-independent Rust (serde, the reducer, the boundary enforcer) compiled from the same source on both platforms. The Windows gap is real, but it belongs to a different claim: writer-lease correctness across a restart, which M5 measured only on Linux. The honest framing is: COMPATIBLE-AT-V5 is sound as a schema verdict; the Windows lease observation is an open durability item that must be completed before Phase 22 ships, but its outcome cannot logically flip the version decision — even if Windows lease behavior needed a fix, that fix would be orthogonal to whether new variants ride v5 or v6. So the verdict does not overreach, provided the bundle's own scoping is respected: it supports the version choice, not the full Windows durability story.
