BACKGROUND
================================================================================

Phase 21's property: every delegated actor stays inside the parent's authority
and resource envelope. Success Criterion 1 is that a child cannot widen ANY of
provider, tool, filesystem, egress, secret, approval, depth, fan-out, time,
token or cost restriction.

Plan 21-01 produced an authority census. Plan 21-02 built a dual-surface hostile
child corpus and measured it INDEPENDENTLY, forbidden from fixing anything: 11
dimensions x 4 combinations (standalone/host-protocol crossed with
in-process/live-against-the-real-binary) x 2 platforms (Linux, Windows) = 88
executions. It recorded ZERO widenings but was explicit that three of the four
census HIGH findings are NOT disproved by that zero.

Plan 21-03 (this one) triages those findings, takes ONE authorization, repairs
ONCE within a hard cap of TWO edit-build-run iterations on real hardware, and
re-measures ONCE. It may not create a further plan. Phase 21 is capped at four
plans total because the previous phase metastasised to seventy-four when its
finding rules had no fixed point.

The amended phase rules, verbatim:
  - Findings at CRITICAL or HIGH must be FIXED or DISPROVED. MEDIUM and below
    are logged to BACKLOG and do not block execution.
  - A REPORTED RED IS WORTH FAR MORE THAN AN ENGINEERED GREEN. Never weaken an
    assertion, #[ignore], #[allow], re-gate, delete a test, or raise a timeout
    to reach a gate.
  - A repair is not CLOSED until the shipped `wayland-core` binary is observed
    refusing the actual widening at a surface a user touches. An in-process
    green against a live red is NOT closed.

DISPROVE means the corpus case asked a question production cannot actually be
asked, so the CASE is corrected and no production code changes. It is a
first-class outcome with equal standing to FIX, and it is the cheapest correct
outcome when it is the true one.

DECLINED means the panel has seen a real finding, weighed it against a measured
cost, and chosen to leave it honestly open with its evidence. It is a decision
on the record, not an oversight.

--- F21-02-01 :: HIGH :: proposed FIX
Seam (census-assigned): crates/wcore-agent/src/spawner.rs :: build_tool_registry

CONFIRMED at the seam, and NOT disprovable. build_tool_registry
(spawner.rs:2396-2445) grants from a fixed six-tool array whatever the child's
`allowed` list names. Neither it nor the AgentSpawner struct (spawner.rs:719-800)
carries any representation of the parent's own tool authority. The permit
expression is:

    let permitted = if allowed.is_empty() { SHARED_READ_ONLY_CHILD_TOOLS.contains(name) }
                    else { allowed.iter().any(|a| a.as_str() == *name) };
    let permitted = permitted
        && (requested_workspace == RequestedChildWorkspace::IsolatedMutation
            || SHARED_READ_ONLY_CHILD_TOOLS.contains(name));

The codebase's OWN existing unit test proves the widening without any new
harness: spawner.rs:4357 tc_7_42_build_tool_registry_destructive_requires_opt_in
calls build_tool_registry(&["Bash","Write"], IsolatedMutation, ...) and asserts
registry.get("Bash").is_some(). A parent restricted to Delegate + Read/Grep/Glob
therefore hands its child Bash whenever an isolated worktree can be prepared.

Concrete change: add parent_tool_authority: Option<Arc<BTreeSet<String>>> to
AgentSpawner with a builder, propagate it in clone_for_spawn, pass it into
build_tool_registry as a new final parameter, and intersect INSIDE that function
so no route into the seam can skip it:

    let permitted = permitted
        && parent_tool_authority.is_none_or(|authority| authority.contains(*name));

Wire it at the single production construction site, bootstrap.rs:2202, where the
parent's own registry is already in scope and ToolRegistry::tool_names() already
exists. Five in-file test call sites gain a trailing None.

FLAGS: not a behaviour change for a correctly-configured session (a parent that
holds Bash still delegates Bash). It IS a behaviour change for any session whose
parent registry is narrower than the child's request -- which is exactly the
amplification. Not an architecture change.

KNOWN RESIDUAL, stated up front: None means "no parent authority recorded" and
applies no intersection, so legacy and test spawners are unaffected. That is
FAIL-OPEN BY DEFAULT -- structurally the same shape as the PolicyGate defect in
F21-02-03. It is chosen because a fail-closed default would deny every tool to
every non-bootstrap spawner, and it is mitigated by a reachability test on the
production bootstrap path. A panel member who thinks this residual disqualifies
the fix should say so.

KNOWN LIVE-CLOSURE PROBLEM, stated up front: the corpus could not reach this
seam live because a hermetic non-repository workspace refuses isolated-worktree
preparation before the child launches. After the fix, the live tool leg would
still read REFUSED -- for the OLD reason. Under this plan's own rule ("a repair
is not closed until the real product refuses the widening"), F21-02-01 may end
NOT-CLOSED on its live leg even when the seam is genuinely repaired, unless the
live fixture is rebuilt as a real git repository with a non-overlapping worktree
root, which is itself a material amount of work inside a two-iteration cap.

Presented in a rotated order. Pros and cons are copied verbatim from the plan.

OPTION id: disprove-and-correct
  Name: Authorize corpus corrections only - the findings are artifacts of invalid
    cases, so the cases are corrected and no production code changes
  Pros: Cheapest correct outcome when it is the true one: the system was right
    and the corpus was slightly wrong, and changing production to satisfy an
    invalid question would have shipped a real behaviour change to fix an
    imaginary defect
  Cons: Available only where Task 1 produced a DISPROVE proposal with evidence;
    selecting it for a finding triaged FIX would be editing the case instead of
    the defect, which is the exact forgery the RED-over-GREEN rule forbids

OPTION id: decline-all
  Name: Decline the whole set - leave every finding open and escalate the phase's
    position
  Pros: Appropriate when the repair set does not fit the plan, when the required
    changes are larger than Phase 21's scope, or when the findings suggest the
    seam design itself needs rethinking rather than patching; the reds stay
    honestly red, which is worth more than an engineered green
  Cons: Phase 21 cannot claim Success Criterion 1; 21-04 records the phase as
    incomplete against its own criteria; phases 22 and 23, which are serial
    behind this one, inherit the open authority questions

OPTION id: authorize-partial
  Name: Authorize a named subset - repair the findings whose fix is contained,
    decline the behaviour or architecture changes and leave those findings open
  Pros: Takes the contained wins now without shipping a default-behaviour change
    or a crate-scope change under time pressure; the declined findings stay
    honestly open with evidence, which is a decision on the record rather than a
    silent gap; keeps the repair inside the two-iteration cap
  Cons: Phase 21 closes with known-open CRITICAL or HIGH findings, so Success
    Criterion 1 cannot be claimed unconditionally and 21-04 must state the
    exception explicitly; the declined work has to be scheduled somewhere, and
    phases 22 and 23 are serial behind this one

OPTION id: authorize-full
  Name: Authorize the full proposed repair set - every CRITICAL and HIGH is fixed
    or disproved as triaged
  Pros: Phase 21's Success Criterion 1 can close on a repaired and re-measured
    state; nothing is left open to be rediscovered by a later phase or by a
    customer; the repair lands at the census-named seams while the measurement
    that justified it is still fresh
  Cons: Available only if Task 1's deliverability estimate says the set fits
    inside two repair iterations; if it includes a behaviour change or an
    architecture change, authorizing the set authorizes those too, and their
    blast radius is every existing session rather than the child path alone
