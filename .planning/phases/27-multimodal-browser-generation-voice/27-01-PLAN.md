<objective>
Establish, by running the shipped binary, whether the standalone and host message paths actually share one bounded, open-once, magic-byte-validated attachment and document intake — then unify the paths that do not, and make provider degradation explicit for documents as well as images.

Purpose: F27-01 asserts one intake path. The repository has at least four that decide bounding, format admission and failure wording independently, and one of them hands a validated path back to a parser that reopens it by name. One of the four already implements the exact discipline the requirement describes, so the target is a generalization of a proven in-tree idiom rather than a new design. The reason this must be measured before it is changed is that a divergence visible in source is not automatically reachable in the shipped product, and repairing an unreachable divergence spends risk for nothing.
Output: A measured intake audit with a severity on every divergence; one shared intake chokepoint that the composer, the document tools and the channel enricher all call; an explicit, user-visible degradation for every attachment class a provider cannot accept; a deterministic intake corpus; and live proof through the real `wayland-core` binary on Linux and native macOS.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| intake ← caller-supplied path | A path arriving from a host composer, a model tool call or a terminal reference is untrusted; everything the product later believes about that file is decided here |
| intake ← file bytes | The bytes themselves are untrusted parser input; a declared extension is a claim, not evidence |
| intake ← connector-fetched bytes | Channel media arrives already fetched by a connector, so it bypasses path validation entirely and must still face the same format decision |
| outbound request ← attachment class | Whatever crosses into a provider request is what that provider's parser sees; a class it cannot accept must be substituted explicitly, never dropped |
| user ← refusal | A refusal the user never sees is indistinguishable from a silent success, and the model will fabricate a cause for it |
