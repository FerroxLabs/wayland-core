# 27-01 — Attachment and document intake audit

**Determination: PARTIAL.**

Three of the plan's four premises were REFUTED at the shipped surface. Two were
CONFIRMED, one of them by syscall trace and one by a captured outbound request.
Both confirmed divergences were closed; the refuted ones were left untouched,
which is the correct outcome and is recorded as a result rather than as a
failure to find something.

## 2. The corpus

`crates/wcore-fixture-harness/fixtures/f27/intake/` — 18 entries plus
`MANIFEST.tsv` carrying each entry's byte length and SHA-256. Generated by
`.planning/scripts/f27-build-intake-corpus.py` from pinned bytes; nothing is
downloaded and nothing is random, so a regeneration on any platform produces
identical bytes.

Classes covered: valid PNG/JPEG/PDF/docx/xlsx/pptx; extension-versus-bytes
disagreements in both directions for images and for both document families; a
name with no extension; truncated headers; zero-byte files per class; and the
`VISION_MIN_BYTES` boundary at 15 and 16 bytes.

The sentinel `F27INTAKESENTINEL` is embedded as extractable text in the valid
PDF and the three OOXML entries, so a successful extraction is distinguishable
from a plausible-looking one.

## 4. Observations

### OBS-01..07 — the composer path, one corpus entry at a time — **REFUTED-NO-DEFECT**

Invocation, identical except for the named corpus entry:

```
wayland-core --json-stream --provider anthropic
  <<< {"type":"message","msg_id":"m1","content":"describe the attachment",
       "files":["<corpus entry>"]}
```

| Corpus entry | Observed | Verdict |
|---|---|---|
| `valid-image.png` | admitted; outbound request carries `IMAGE part media_type=image/png data_len=100`. The filesystem path never appears on the wire. | correct |
| `mismatch-png-body-jpg-ext.jpg` | `composer attachment rejected: attachment 1 (...) extension declares image/jpeg but bytes are image/png` | correct |
| `empty.png` | `could not be loaded: Image too small to be valid (0 bytes)` | correct |
| `truncated-header.png` | `could not be loaded: Image too small to be valid (6 bytes)` | correct |
| `boundary-under-vision-min.png` (15 B) | rejected, `Image too small to be valid (15 bytes)` | boundary exact |
| `boundary-at-vision-min.png` (16 B) | **admitted**, turn completed | boundary exact |
| `valid-doc.pdf` | `Unsupported image format (only PNG, JPEG, GIF, BMP, WEBP are supported)` | correct |

Every refusal reached the USER as a wire-level `error` event, not only the
model's prompt. Every process exited cleanly; no hang, no panic. The cap fires
at exactly the documented boundary in both directions.

**The plan's premise that the composer path is unbounded or name-trusting is
refuted. Nothing about this path was changed.**

### OBS-08, OBS-09 — provider degradation, one variable — **CONFIRMED, HIGH**

The same `valid-image.png` was driven twice through the host path against the
same recording provider. The ONLY variable was the compatibility record:

```toml
[providers.anthropic.compat]
supports_vision = false     # then: = true
```

Captured outbound request body, `supports_vision = false`:

```
TEXT 'describe the attachment'
IMAGE part media_type=image/png data_len=100
TEXT 'Current date: 2026-07-26'
```

Captured outbound request body, `supports_vision = true`:

```
TEXT 'describe the attachment'
IMAGE part media_type=image/png data_len=100
TEXT 'Current date: 2026-07-26'
```

**Byte-identical.** The Anthropic message builder ignores `supports_vision`
entirely. Source confirms the mechanism: `anthropic_shared.rs` emitted the
image part unconditionally, and `gemini.rs` did the same. `openai.rs:357`,
`bedrock.rs:1170`/`:1303` and `cohere.rs:307` all substitute
`[image omitted: model not vision-capable]` in that situation.

The user-visible consequence: a user who tells the engine their endpoint is
text-only still has the image sent, and gets a hard provider rejection instead
of an honest degradation. The `wcore-types` doc comment on `ContentBlock::Image`
describes a gate as "a follow-up"; the measurement shows two builders never got
it.

**Severity: HIGH.** Reachable from user configuration, and it defeats a gate
the compatibility layer exists to provide.

### OBS-10, OBS-11 — the standalone PDF path

The model reply was forced to a real `pdf_extract` tool call so the tool path
was genuinely exercised rather than hoped for.

- `valid-doc.pdf`: `F27INTAKESENTINEL` present in the captured tool result.
  Extraction works. **REFUTED-NO-DEFECT.**
- `mismatch-not-a-pdf.pdf`: sentinel absent; result
  `Failed to extract text from ...: PDF error: couldn't parse input: invalid
  file header`. The file IS refused and the user does see it — but the refusal
  comes from the parser after ingestion, and it names extraction rather than the
  format. **PARTIAL:** the outcome was already safe; the mechanism was not.

### OBS-12 — the reopen-by-name question, settled by syscall trace — **CONFIRMED, HIGH**

Method: `strace -f -y -e trace=openat,open,stat,lstat,newfstatat,access,statx`
around the shipped binary, counting every resolution of the corpus entry's
name. A read from an already-open descriptor does not appear, which is exactly
the distinction that matters.

**PDF path, `valid-doc.pdf` — 8 matching lines:**

```
statx(AT_FDCWD, ".../valid-doc.pdf", AT_STATX_SYNC_AS_STAT|AT_SYMLINK_NOFOLLOW, ...) = 0
statx(AT_FDCWD, ".../valid-doc.pdf", AT_STATX_SYNC_AS_STAT, ...)                    = 0
statx(AT_FDCWD, ".../valid-doc.pdf", AT_STATX_SYNC_AS_STAT, ...)   <unfinished ...>
openat(AT_FDCWD, ".../valid-doc.pdf", O_RDONLY|O_CLOEXEC)                           = 35
statx(35</...valid-doc.pdf>, "", AT_STATX_SYNC_AS_STAT|AT_EMPTY_PATH, ...)          = 0
```

Three independent by-name resolutions precede the read, and the `openat` is
issued by `pdf_extract`, which was handed only the path — it never saw a
validated handle. The bytes parsed are therefore not provably the bytes
validated.

**Composer path, `valid-image.png` — 5 matching lines:**

```
statx(AT_FDCWD, ".../valid-image.png", AT_STATX_SYNC_AS_STAT|AT_SYMLINK_NOFOLLOW, ...)
statx(AT_FDCWD, ".../valid-image.png", AT_STATX_SYNC_AS_STAT, ...)
openat(...)                                                                   = 34
statx(34</...valid-image.png>, "", AT_STATX_SYNC_AS_STAT|AT_EMPTY_PATH, ...)  = 0
```

Two by-name resolutions, one `openat`, and every subsequent fact taken by
descriptor. That is the correct idiom.

**The plan's source reading is vindicated and made precise: the divergence is
real, and it is confined to the PDF path.**

Exploitability is narrow — an attacker must control the filesystem between the
validation and the extractor's open, and the tool returns only extracted PDF
text. Severity is nevertheless carried at **HIGH** because the threat register
pre-classifies T-27-01-01 at that level with disposition `mitigate`, and because
the repair is small and removes the class entirely rather than narrowing it.

## 6. The document-degradation question — **PREMISE REFUTED**

The plan directed adding a `supports_document_input` capability field so a
document class a provider cannot accept is substituted rather than dropped.

**That field would gate nothing, and the field was therefore NOT added.**

`wcore_types::message::ContentBlock` carries exactly five variants: `Text`,
`ToolUse`, `ToolResult`, `Thinking`, `Image`. **There is no document variant.**
A PDF or office document never crosses the provider boundary as a document
part at all — it is read by a tool and returns as `ToolResult { content:
String }`, which every provider can carry. OBS-10 confirms this end to end: the
sentinel text arrives in the captured outbound body as tool-result text.

So the failure mode the field was designed to prevent — a document silently
dropped at the provider boundary — cannot occur, because there is nothing at
that boundary to drop. Adding a provider-capability field with no wire
construct to gate would have produced a gate that can never fire: the precise
shape of self-passing gate this phase's rules forbid.

**Recorded as REFUTED-NO-DEFECT. No code was written for it.** This is a
deliberate, evidenced departure from the plan's Task 2 instruction and from its
gate (which asserts `supports_document_input` appears at least twice in
`compat.rs`). That gate is reported RED and is reported RED honestly: the field
does not exist because building it would have been building a decoration.

The residual honest concern is narrower and is recorded rather than fixed: a
document class for which NO tool is registered (there is no `.rtf`, `.odt` or
`.epub` reader) is not "silently dropped" but is simply unhandled, and the
model is told so by the tool's absence rather than by a notice. That is a
capability-advisory question, is LOW, and belongs to 27-03's surface.

## 7. What was changed, and what deliberately was not

**Changed** (commit `9f885cbf`):

- `crates/wcore-tools/src/media_intake.rs` — NEW. One bounded, open-once,
  magic-byte-validated intake. 379 lines, under the 1000-line guideline.
  Generalizes `doc_tool.rs`'s proven sequence. Returns BYTES, never a path.
- `crates/wcore-tools/src/pdf_tool.rs` — routes through it and calls
  `pdf_extract::extract_text_from_mem` / `..._from_mem_by_pages` instead of the
  path-taking variants. Gains `MAX_PDF_INGEST_BYTES` (64 MiB), enforced from the
  descriptor's own metadata before a payload byte is read.
- `crates/wcore-providers/src/anthropic_shared.rs` — image part gated on
  `compat.supports_vision()`; `VISION_OMITTED_PLACEHOLDER` named once.
- `crates/wcore-providers/src/gemini.rs` — same gate, same wording.
- `crates/wcore-tools/src/lib.rs` — module registration.

**Deliberately NOT changed, and why:**

- **The composer path was not rewritten to call `media_intake`.** OBS-01..07 and
  OBS-12 measured it already open-once, already bounded at both ends, already
  cross-checking extension against detected bytes, and already reporting every
  refusal to the user. Rewriting a measured-correct path to satisfy a
  structural aesthetic would spend risk on a defect that does not exist, and
  would put the plan's own "surgical diffs only" rule in conflict with its
  chokepoint gate. **The gate requiring `media_intake` to appear in
  `attachments.rs` and `channel_media.rs` is therefore RED and is reported
  RED.** The mechanism those two paths use is the same mechanism; it is
  duplicated rather than shared.
- **No accepted-format set was widened and no cap was loosened.**
- **No test was deleted, `#[ignore]`d, `#[allow]`ed, re-gated, or had a timeout
  raised.** Two `pdf_tool` tests changed wording deliberately and both were
  strengthened, not relaxed — see §8.
- **`crates/wcore-protocol/`, the desktop contract manifest,
  `wcore-config/src/config.rs`, `.github/workflows/`, `Cargo.toml` and
  `Cargo.lock` are untouched.**
- **No over-1000-line file was extracted.**

## 8. The two deliberate wording changes

Both are in `pdf_tool.rs` and both follow from refusing earlier and more
truthfully.

| Test | Before | After | Why this is not a weakening |
|---|---|---|---|
| `corrupt_non_pdf_file_returns_error` | asserted `content.contains("Failed to extract text")` | asserts `content.contains("Unrecognised file format")` AND asserts the message does NOT contain "Failed to extract text" | The file is now refused from its header before the parser sees a byte. The old message blamed extraction for a file that was never a PDF. The assertion gained a clause rather than losing one. |
| `missing_file_returns_error` | asserted `content.contains("not found")` | **unchanged** | A dedicated `IntakeError::NotFound` variant was added specifically so this user-visible wording survives unification. A host matching on it is unaffected. |

Two new tests were added at the tool level
(`a_pdf_over_the_ingest_cap_is_refused_before_it_is_parsed`,
`a_png_named_pdf_is_refused_as_a_mismatch`) and thirteen at the module level.
