## Part one — the paired tamper corpus

**Tamper rejection is proved by tampering, never by signing and verifying.** Every row
below is a pair: the pristine subject was verified and **ACCEPTED**, then exactly one
field or one byte was mutated and the same verification **REFUSED** it. Both halves ran,
in that order, for every case.

The pairing is enforced by the type, not by review. `TamperCase::new` constructs the
pristine subject itself and `Paired::new` takes it as a mandatory argument, so a case
carrying only a mutation cannot be written. `Paired::new` additionally refuses a mutation
that changes nothing, which would make the pair vacuous in the other direction.

No case asserts a rendered error string. Each asserts only the invariant that the input
was refused. The **refusal point** column is recorded for the reader and is never
asserted by a case — pinning a message encodes today's failure shape and keeps passing
when the refusal moves to a different and possibly weaker cause.

### The subject

One signed release manifest plus the object store it binds:

| Object | What it actually is |
|---|---|
| `wayland-core-x86_64-unknown-linux-gnu.tar.gz` | the first mebibyte of the real compiled `wcore-eval-fixture` binary this workspace builds |
| `wayland-core-sbom.cdx.json` | a real CycloneDX SBOM generated by the product's own `sbom::cyclonedx_from_cargo_metadata` from the pinned `fixtures/f29/cargo-metadata.json` |
| `wayland-plugin-ollama-0.12.25.tar.gz` | a deterministic plugin payload |
| `receipt-body.json` | the body of a receipt the **real evaluation pipeline** emitted in-process during the test run |

Verified by, in order: the shipped `verify_manifest` against an independently supplied
trust root; the shipped `sbom::sbom_sha256`; the certification join recomputed through
`EvidenceReceiptV1::local`; then digest-and-length equality for every packaged artifact.
The manifest is verified under role `release_acceptance`, which is the role
`wcore-cli`'s shipped updater pins as `RELEASE_MANIFEST_ROLE`.

| F29-03-SBOM-1 | SBOM | one byte of the CycloneDX SBOM document | ACCEPTED | REFUSED | SBOM digest |
| F29-03-UPDATE-1 | update | manifest `sequence` lowered by one, not re-signed | ACCEPTED | REFUSED | signed manifest |

**Zero cases whose result was not accept-then-refuse.** Twelve controls accepted, twelve
mutations refused, seven object classes covered, three distinct attacks in the key class.

Note that BACKEND-RECEIPT-1 and BACKEND-RECEIPT-2 refuse at **different points**, and
that is the point of having both. -1 mutates the manifest, so the body digest and the
signature disagree. -2 leaves the manifest completely untouched and mutates the receipt
it names, so `verify_manifest` still passes and the refusal comes from the join itself.
Only -2 proves the join is real.

### The corpus can go red — proved four ways

A corpus that passes proves nothing until it has been shown to fail. Four deliberate
defects were introduced one at a time, each run, each restored from a pristine copy held
outside the worktree (`tamper-negative-controls.txt`):

| Control | Defect introduced | Result |
|---|---|---|
| NC-1 | one case's mutation replaced with a no-op | **rc=101** — `Paired::new` refuses to build a pair whose halves are identical |
| NC-2 | the pristine manifest signed with the WRONG role key, so every control is refused | **rc=101** — "the PRISTINE control must be ACCEPTED"; this is exactly the rejection-only shape a verifier that refuses everything would pass |
| NC-3 | the SBOM case deleted from the table | **rc=101** — the class-coverage meta-assertion fires |
| NC-4 | one case's mutation replaced with a change the verifier ignores (`subject.now += 1`) | **rc=101** — the pair builds because the halves differ, but the REFUSAL assertion fires, proving that half is live |

Tree after the campaign: `dirty_paths_under_crates=0`, and the restored corpus went green
again (`restored_rc=0`).

### What this corpus does NOT cover, stated rather than implied

- **The update class is proved at the release-manifest layer only.**
  `wcore-eval-scenarios` has no dependency edge on `wcore-cli`, and adding one is a
  `Cargo.toml` change outside this plan's declared paths. The shipped updater's own
  `update_trust::verify_manifest_json` and `check_archive` were driven live against the
  real binary by 29-03 (19 mutations applied, 18 caught). This corpus mutates the exact
  manifest fields that updater reads — `sequence`, `issued_at`, the artifact digests —
  through the same signed-manifest verifier.
- **The plugin and backend classes are proved at the release-manifest layer only.**
  Their runtime install-time trust root is `INDEX_PUBKEY_HEX` in
  `crates/wcore-cli/src/plugin/index.rs`, which still carries the all-zeros placeholder
  and belongs to Phase 25. That is F29-LIMIT-03 and it is why Success Criterion 3 is not
  graded MET. It is named here rather than absorbed.
- **The receipt's own signature chain is Phase 28's.** This corpus proves the *binding*
  between a release manifest and a receipt. Whether the receipt itself is authoritative
  is `receipt.rs`'s question, and 29-01 already proved that surface.

## Part two — the four release states, run twice through the real binary

Both runs were driven through the real `wayland-release` binary built at the pinned
commit with `cargo build --release --locked`. Not library calls: the binary a release
engineer would actually run.

### Run A-1 — all four role keys, through the shipped tool only

The honest production measurement, recorded first because it is the one that describes
today's tooling.

```
[A1 append packaging]               rc=0  STATE APPENDED state=packaging
[A1 append deployment_preparation]  rc=0  STATE APPENDED state=deployment_preparation
[A1 append rollback_rehearsal]      rc=0  STATE APPENDED state=rollback_rehearsal
[A1 append release_acceptance]      rc=0  STATE APPENDED state=release_acceptance
[A1 state-verify]                   rc=1  release acceptance requires an observed certification binding
```

**Holding every key is not sufficient.** The acceptance record was minted — the append
succeeded — and the chain still refused to be accepted. Possession of a signature is not
authority. This is correct fail-closed behaviour and it is the second, independent gate
on release acceptance.

It also surfaces a finding: **`wayland-release manifest build` hardcodes
`certification: Evidence::Unavailable` and offers no flag to record a binding**, so the
four-state chain cannot be completed through the shipped tooling at this commit. That is
**F29-04-01**, recorded below and not repaired here.

### Instantiating the Phase 28 seam in the clean room

To obtain the positive control Criterion 4 needs, the binding was filled from a receipt
the **real evaluation pipeline** produced on this machine:

```
[wayland-eval fixture run] rc=0   PASS canary deepseek os=linux approval=yolo
[wayland-receipt sign]     rc=1   fixture digest is a synthetic binary/scenario label,
                                  not fixture provenance
```

**The CI-sign refusal is a result, not an obstacle.** The product refuses to mint a CI
authority claim over a receipt whose fixture provenance is synthetic. That guard is
correct and this lane did not bypass it — minting the signature by hand in Python would
have defeated exactly the control the phase exists to defend. So the clean-room binding
names a **LOCAL-authority** receipt and says so in its own field
(`receipt_signing_key_id = local-authority-unsigned-no-ci-signature`). A real binding
needs a CI-signed receipt from a real evaluation run: **F29-LIMIT-07**.

The binding carries the real receipt's real values:

| Field | Value |
|---|---|
| `receipt_body_sha256` | `6a3ad4f9…` (as computed by the product) |
| `receipt_schema` / `_version` | `wayland.eval.receipt` / `1` |
| `source_commit` | `0123456789abcdef0123456789abcdef01234567` |
| `binary_sha256` | `2d868f5e…` |
| `target_os` / `_architecture` | `linux` / `x86_64` |

The manifest body was then re-digested and signed and verified **by the real binary**:

```
[manifest-sign(A)]   rc=0  MANIFEST SIGNED   body_sha256=d361c3e3…
[manifest-verify(A)] rc=0  MANIFEST VERIFIED body_sha256=d361c3e3…
```

`manifest-verify rc=0` is the self-check: had the recomputed digest differed from what
the product computes by a single byte, this step would have failed with a digest
mismatch. It did not.

### Run A — the positive control

```
[A append packaging]                rc=0
[A verify prefix[1]]                rc=0  CHAIN VERIFIED highest_state=packaging               records=1 accepted=false
[A append deployment_preparation]   rc=0
[A verify prefix[2]]                rc=0  CHAIN VERIFIED highest_state=deployment_preparation  records=2 accepted=false
[A append rollback_rehearsal]       rc=0
[A verify prefix[3]]                rc=0  CHAIN VERIFIED highest_state=rollback_rehearsal      records=3 accepted=false
[A append release_acceptance]       rc=0
[A verify prefix[4]]                rc=0  CHAIN VERIFIED highest_state=release_acceptance      records=4 accepted=true
```

Four states reached, four distinct role keys, four disjoint evidence sets, each record
binding the previous record's digest.

### Standalone verification — each record against only its own role key

A chain that verifies only as a chain is sequential, not separable. Each record's
signature was checked by **OpenSSL 3.0.13** — an implementation with no stake in the
outcome — using only that record's own role public key:

```
[STANDALONE packaging              with role=packaging              key] rc=0 Signature Verified Successfully
[STANDALONE deployment_preparation with role=deployment_preparation key] rc=0 Signature Verified Successfully
[STANDALONE rollback_rehearsal     with role=rollback_rehearsal     key] rc=0 Signature Verified Successfully
[STANDALONE release_acceptance     with role=release_acceptance     key] rc=0 Signature Verified Successfully
```

Paired with **twelve cross-role controls** — every record against every *other* role's
key — all twelve `rc=1 Signature Verification Failure`. Without those, four successes
would be equally consistent with a verifier that accepts anything.

### Run B — the release-acceptance key withheld

Three keys in the trust root, three seeds on disk. Run B cannot mint an acceptance record
at all: there is nothing to sign with.

```
trust root reduced from 4 keys to 3: no release_acceptance role
    -rw------- deployment-preparation-key.seed
    -rw------- packaging-key.seed
    -rw------- rollback-rehearsal-key.seed
[B state-verify] rc=0  CHAIN VERIFIED highest_state=rollback_rehearsal records=3 accepted=false
```

**rc=0, not rc=1.** A missing record is a *stopping point*, not a corrupt chain, which is
the honest answer when a state's key is legitimately unavailable. `accepted=false` is the
single predicate a release gate consults, and it cannot be satisfied without a signature
from the release-acceptance key.

### Seven collapse attempts, every one refused

Each executed as a real invocation against run A's otherwise-valid chain, so exactly one
thing is wrong per attempt.

| # | Attempt | rc | Refusal |
|---|---|---|---|
| 1 | relabel the packaging record as release acceptance | 1 | `record at position 0 is ReleaseAcceptance but canonical order requires Packaging` |
| 2 | sign an acceptance record with the packaging role key | 1 | `key id packaging-key signs more than one state in the same chain` |
| 3 | acceptance evidence reuses a packaging digest | 1 | `state ReleaseAcceptance reuses evidence digest 0ee28680… from an earlier state` |
| 4 | verify a chain with deployment preparation removed | 1 | `record at position 1 is RollbackRehearsal but canonical order requires DeploymentPreparation` |
| 5 | verify a chain with two states swapped | 1 | `record at position 1 is RollbackRehearsal but canonical order requires DeploymentPreparation` |
| 6a | `state-append --state termination_state_4` | 2 | `invalid value 'termination_state_4' … unknown release state` |
| 6b | a fifth record with `state: "termination_state_4"` spliced into the chain JSON | 1 | `unknown variant 'termination_state_4', expected one of packaging, deployment_preparation, rollback_rehearsal, release_acceptance` |
| 7 | acceptance signed by a **freshly rotated packaging-role key** | 1 | `key spare-packaging-key is bound to role Packaging but role ReleaseAcceptance is required` |

Attempt 7 exists because attempt 2 was refused by the distinct-key-per-state rule, which
fires *before* the role check — so attempt 2 alone does not prove the role binding. With
a fresh key id, no id repeats and the refusal comes from the role.

Attempt 6 uses the exact state name an agent on this program actually invented to route
around an artifact it wrongly believed unobtainable. Both doors were tried; both are shut,
and 6b is shut at **deserialization**, before any logic runs.

### The two sentences that must appear together

**The release-acceptance mechanism is proved.** Run A completed the four-state chain
through the real binary and reported `accepted=true`, with each record independently
verifiable against only its own role key.

**No release was accepted.** The key that completed run A was generated at run time into
a temporary directory and died with the run. The real release-acceptance key is Sean's;
this lane neither holds it nor requests it; nothing was published, tagged, merged or
released. A clean-room chain completing is the mechanism working. It is not an
authorization, and it must never be read as one.
