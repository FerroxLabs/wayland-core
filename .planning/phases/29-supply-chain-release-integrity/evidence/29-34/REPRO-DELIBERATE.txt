SUPPLY-29-34 -- MAKING REPRODUCIBILITY DELIBERATE
Host: hetzner-dsm. Target: cargo build --release --locked -p wcore-cli
      (the binary release.yml ships, ~98 MB).

==========================================================================
THE EXPERIMENT
==========================================================================
Two clean checkouts of the SAME commit at DIFFERENT-LENGTH absolute paths:

  A = /root/wl-s2934/alpha                      (21 chars)
  B = /root/wl-s2934/beta-considerably-longer    (39 chars)

Different LENGTHS on purpose. 29-02 used /root/f29-repro/a1 and .../a2, which
are equal-length, so an equal-length substitution could have masked a
size-sensitive effect -- and 29-02 in fact observed a size delta it had to
explain via string-table tail-merging. Unequal lengths remove that confound.

Everything else held fixed across every arm: same commit, same lockfile
(--locked), same toolchain (cargo 1.95.0 / rustc 1.95.0 from the repo pin),
same host, same shared cargo registry, same profile, CARGO_BUILD_JOBS=10.
Each tree keeps its own target/ -- never a shared CARGO_TARGET_DIR, because
wcore-protocol bakes CARGO_MANIFEST_DIR into a digest and a shared target
would have poisoned exactly this measurement.

BOTH DIRECTIONS ARE RUN. An experiment that can only report "reproducible"
is as useless as one that can only report "not reproducible". Arm A is the
known-negative: it must DETECT non-reproducibility. Arms B..D are the
treatment.

The remap WORKS, and works well: all 7 cranelift OUT_DIR strings gone, all
1619 registry paths gone. And the digests still differ, because of ONE
surviving literal:

  <tree>/crates/wcore-cli

sitting in the string table next to WAYLAND_TEMPLATES_DIR, plugin-static,
plugin-wasm and "repointed wcore-plugin-api at the in-tree crate".

**THE FILED REMEDY WAS NECESSARY BUT NOT SUFFICIENT.** Had 29-02's
--remap-path-prefix been applied and believed, the release would have been
declared REPRODUCED while still not being reproducible. That is the finding.

WHY THE REMAP CANNOT REACH IT. The literal comes from
env!("CARGO_MANIFEST_DIR"), which rustc expands to a STRING LITERAL before
any path remapping applies. Cargo's own documentation says the path
sanitizing settings "do not affect hard-coded paths within source code
strings". So no amount of --remap-path-prefix will ever remove it.

AND trim-paths IS NOT AVAILABLE. Probed rather than assumed, with a
throwaway crate:
  error: failed to parse manifest
  Caused by: feature `trim-paths` is required
    ... that feature is not stabilized in this version of Cargo
        (1.96.0 (30a34c682 2026-05-25))
It would not have been sufficient either: trim-paths exposes CARGO_TRIM_PATHS
for build scripts to honour VOLUNTARILY, and offers nothing for a hard-coded
source string.

Incidental, worth recording: hetzner's ambient default toolchain is 1.96.0
while the repo pin resolves to 1.95.0. A bare `cargo` outside a repo tree is
a different compiler from the one that builds this workspace.

WHAT STILL DIFFERS, LOCATED EXACTLY. Diffing the sorted string sets leaves
45 strings unique to each binary, and they are all one shape:
  alpha: anon.68701565214d472e099372474bc73ec8.333.llvm.15554408849794364881
  beta : anon.68701565214d472e099372474bc73ec8.333.llvm.8592441538425800383
The anon prefix hash is IDENTICAL. Only LLVM's trailing module-ID differs,
and the two ids have 20 and 19 digits -- which accounts for the 45-byte
string-table delta (readelf: 0xa05a22 vs 0xa059f5) and the 48-byte file
delta. These are LLVM internal-linkage symbol suffixes living in .symtab.

ROOT CAUSE, AND WHY IT IS NOT FIXABLE BY REMAPPING. The module id is derived
from the crate's `-C metadata` hash, which Cargo computes from the package's
SourceId -- and for a workspace path dependency the SourceId CONTAINS THE
ABSOLUTE PATH. There is no stable Cargo knob to canonicalize it.
`--remap-path-prefix` operates on source spans and cannot reach it.

==========================================================================
IS THE RESIDUAL REMOVABLE?  Post-hoc strip test, both directions.
==========================================================================
The profile ships `strip = "debuginfo"` (Cargo.toml:566), which drops debug
info but KEEPS .symtab -- exactly where these symbols live.

  strip --strip-all on the ARM-D (remapped) pair:
    sizes 84265208 / 84265208  -- IDENTICAL
    contents DIFFER by 20 BYTES

  strip --strip-all on the ARM-A (unremapped) control pair:
    contents DIFFER by 4,096,883 bytes
    -> strip ALONE is not sufficient; the remap is doing the real work.

Twenty bytes is the length of a SHA-1, i.e. the GNU build-id -- which 29-02
already established is "a CONSEQUENCE, not an independent cause": it hashes
the linked content, and the content differed before stripping. Stripping
post-hoc cannot retract a build-id already computed over unstripped input.

So the prediction is that stripping AT LINK TIME, so the symbols never exist
when the build-id is computed, closes the last 20 bytes. That prediction is
tested in ARM E rather than asserted.

==========================================================================
THE RECIPE, AND WHAT OF IT IS LANDED
==========================================================================
Three ingredients, and all three are required -- each was measured
individually and none is sufficient alone:

  1. Gate BOTH env!("CARGO_MANIFEST_DIR") sites in
     crates/wcore-cli/src/plugin/scaffold.rs behind #[cfg(debug_assertions)].
     LANDED on this lane branch (5fa47abd). No behavioural cost: both
     branches are already no-ops for an installed binary, and the debug
     unit tests are unchanged at 5 passed / 0 failed.

  2. --remap-path-prefix for the tree, the registry and the cargo git dir.
     NOT LANDED -- see below.

  3. -Cstrip=symbols. NOT LANDED, and NOT RECOMMENDED WITHOUT A DECISION.

ON (2). Free of behavioural cost and worth having on its own merits: it
removes 7 cranelift paths, 1619 registry paths and the builder's directory
layout from the shipped artifact. It is NOT wired into release.yml here for
one concrete, unresolved reason: release.yml builds the linux-aarch64 target
through `cross`, which compiles inside a container where the source is
mounted at a DIFFERENT path (/project), so a
`--remap-path-prefix=$GITHUB_WORKSPACE=...` would silently fail to match on
exactly that leg while appearing correct on the others. That is precisely the
shape of a gate that passes without measuring anything, and it is not
testable from this lane. Wiring it requires a per-leg prefix and a
cross-container check.

ON (3). `-Cstrip=symbols` removes .symtab, so production panic backtraces
lose function names. The profile deliberately ships `strip = "debuginfo"`
(Cargo.toml:566), which is a considered choice to keep them. Trading
diagnosability for the final 48 bytes of reproducibility is a PRODUCT
decision with a real cost on both sides, and this lane does not make it
unilaterally on a shared profile that every other lane builds against.

WHAT THE VERDICT SHOULD SAY. Not "REPRODUCED". The honest grade is:
reproducibility is now DEMONSTRABLY ACHIEVABLE with a named, measured,
three-part recipe, and one third of that recipe is landed. The variance is
no longer "documented" in the sense of merely explained -- it is closed
under a recipe that was executed and produced identical bytes. What remains
is a wiring task with a known obstacle (cross) and one product decision.
