<objective>
Measure what the shipped supply chain actually does, then land the three data structures the rest of the phase is built on: a signed release manifest, a role-scoped trust root, and a closed four-state release ledger — all provable end to end with an Ed25519 trust root generated at run time into a temporary directory.

Purpose: F29-01 and F29-04 are usually planned as documents. This repository has already been burned by both failure modes they invite: a declared policy that nothing runs (`deny.toml`), and an agent inventing an extra termination state to get past a wall. The countermeasure is to make the state separation a type that refuses an unknown state name before any logic runs, and to make every trust claim verifiable against a key that this lane can generate and that Sean's real key later substitutes for in exactly one place.
Output: a measured supply-chain census with a severity on every gap; an explicit written interface stating what Phase 29 requires from Phase 28's certification receipts and what 28 must add; and a release-integrity module plus `wayland-release` binary whose contract suite proves domain separation, role-key binding, evidence disjointness and the structural unreachability of release acceptance without Sean's key.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| release manifest ← untrusted document | A manifest arriving from a registry, a mirror or a peer is a claim; nothing inside it may establish its own authority |
| trust root ← operator | The trust root is the only thing this system believes without proof, so it must arrive independently of every document it validates |
| state record ← state key | Each state's authority is a separate key; if one key can mint another state's record, the four states are one state wearing four labels |
| certification binding ← Phase 28 receipt | A receipt is produced by a different phase on different hardware; 29 must verify it, never assume it, and must be able to represent its absence honestly |
| signing seed ← process boundary | A seed on an argv is visible in the process table and in shell history; a seed on stdout is visible in every log that captured the run |
