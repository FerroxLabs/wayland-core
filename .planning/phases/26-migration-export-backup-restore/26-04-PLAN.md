3. **Isolation prevents; the SHA assertion DETECTS.** Every remote gate asserts the tree is at this plan's SHA immediately before the work and again immediately after it — on Linux in the worktree, on Windows in the shared checkout — so anything that moved it mid-flight turns the gate RED instead of yielding a green that does not match its claimed SHA. On Windows, chaining several `cmd /c` calls and reading one trailing `$LASTEXITCODE` reports only the LAST step's status: a draft of this plan's Windows build gate ran fetch, then checkout, then build under a single trailing status, so a FAILED checkout followed by a successful build of the OLD tree would have reported green on the wrong commit. Every Windows step therefore checks its OWN status, and the SHA is proven by capturing `git rev-parse HEAD` ALONE to its own file and comparing the fetched value.

**A FIFTH TRAP — MEASURED ON THE REAL BOX, AND IT MADE EVERY WINDOWS GATE IN AN EARLIER DRAFT OF THIS PLAN INCAPABLE OF GOING RED.** The Windows sshd default shell is PowerShell, so `ssh SeanD@seandesktop "powershell -NoProfile -Command \"…\""` passes through TWO PowerShell layers, and the OUTER one expands `$LASTEXITCODE` — empty at that point — before the inner one sees it. Measured: `ssh … "powershell -NoProfile -Command \"cmd /c 'exit 42'; exit \$LASTEXITCODE\""` returns **0**, and an inner `if (\$LASTEXITCODE -ne 0)` arrives as the syntax error `if ( -ne 0)`. The two forms need OPPOSITE escaping, both measured in both polarities: a `-Command` gate escapes with a PowerShell backtick, written `` \`\$LASTEXITCODE `` (fails non-zero on `exit 42`, returns 0 on `exit 0`); a `-File script.ps1; exit \$LASTEXITCODE` gate does NOT, because there is only one layer and its `$LASTEXITCODE` genuinely is the child's code (returns 7 on `exit 7`, 0 on `exit 0`) — backticking that form makes the shell try to RUN `$LASTEXITCODE`, a guaranteed red, which is just as useless. The numeric code is flattened to 1 through the `-Command` path, so the distinct per-step codes do not survive as numbers; the `STEP-FAIL: <step>` marker each step prints does, and that marker is what identifies the failing step.

The Linux shape, used by every Linux gate in this plan:

`SHA=$(/usr/bin/git rev-parse HEAD); WT=/root/wayland-f26-04; ssh -o BatchMode=yes hetzner-dsm "set -e; export PATH=/root/.cargo/bin:\$PATH; cd /root/wayland; /usr/bin/flock /tmp/wayland-fetch.lock git fetch --all --prune; git worktree add --detach $WT $SHA 2>/dev/null || git -C $WT checkout --detach $SHA; test \"\$(git -C $WT rev-parse HEAD)\" = $SHA; cd $WT; «WORK»; test \"\$(git -C $WT rev-parse HEAD)\" = $SHA" > «LOG» 2>&1; rc=$?; tail -30 «LOG»; test $rc -eq 0`

`set -e` makes any step's failure the ssh exit status; the status is captured on its own line and tested BEFORE the log is read; no filter ever sits between the command and its status. This is the phase's LAST plan, so after its final Linux gate passes it removes not only its own worktree but every `/root/wayland-f26-0*` worktree this phase created, with `git worktree remove --force <path>` for each followed by `git worktree prune` — leaving the box as it found it. A FAILED gate leaves them for forensics.

**THE MEASUREMENT TRAPS — ALL FOUR LIVE. Do not simplify them away.**
1. **Mac `grep` is rtk-proxied and SILENTLY DROPS LINES.** Every gate invokes `/usr/bin/grep` explicitly, `-F` for literals. This matters more here than anywhere: a dropped line in a hostile-case report is a missed defect.
2. **A pipe replaces the exit status you care about.** Redirect to a file, capture the return code on its own line, test it, then read. Never filter inside a gate.
3. **Reading an exit code from a block that also emits output** returns an array and makes the comparison always truthy. Read the status on the line AFTER the pipeline.
4. **In `cmd`, an assignment chained with `&&` appends a trailing space** that Rust silently ignores. Use the quoted form and prove the value took effect.

**A FIFTH TRAP SPECIFIC TO THIS PLAN.** Creating a hostile fixture on a case-insensitive or normalizing filesystem SILENTLY DESTROYS the very property under test: writing two names that differ only in case or normal form yields ONE file on the Mac and on Windows.
