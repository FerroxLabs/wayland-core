# KR-01 — TESTED. It does NOT reproduce as characterised, and the carried red is misattributed.

**Carried ledger row** (`evidence/28-01/known-red.tsv`):

> `KR-01` | *descendant process tree is not reaped; a process survives its owner*
> (`wcore-sandbox::live_integrity::live_future_drop_reaps_descendant_job_tree`, Windows,
> deterministic) | p28_severity **HIGH** | contradicted_criterion **2** | dispositions
> **FIXED, DISPROVED** | disposition **OPEN**

28-03 predicted it would reproduce under soak conditions and force Criterion 2 NOT MET on
Windows, and recorded that *"that prediction was never tested"*. It has now been tested.

## VERDICT

**The test fails. It does NOT fail for the reason the ledger records, and it never evaluates
the property the ledger names.** The reap assertion is never reached.

The ledger's subject matter — "a process survives its owner" — is not what the observed red
shows. What it shows is that the sandboxed command **cannot read its own script and exits
immediately**, so no descendant is ever created and there is nothing to reap.

## What makes this more serious than a stale known-red

**The fix for this already landed.** Commit `2b662fe8` ("fix(sandbox): own and reap process
trees", 2026-07-14) is **ancestral to the candidate** — it added `process_tree.rs`'s ownership
guards, `process_capture.rs`, **and this very test** (`tests/live_integrity.rs`, +87 lines) in
one change. So the situation is not "an untested known-red"; it is **a landed fix whose own
acceptance test has been red ever since, and the red was attributed to the defect the fix was
meant to close.** That attribution is wrong, which means the ledger has been carrying a HIGH
row against Criterion 2 on evidence that does not support it.

## The measurement

Run on `SeanD@seandesktop`, via a scheduled task with an explicit exit marker, at lane HEAD
`eecfc331`. `crates/wcore-sandbox` tree `d785593f5e3cd6065ff601652ad91a7ba0ecd954` — **byte
identical to the candidate `e4a3f5fc`'s**, verified on the host, and its only internal
dependency `wcore-types` (`fbc1d457…`) is identical too. So this result transfers to the
candidate exactly.

### The failure, in full

```
thread 'live_future_drop_reaps_descendant_job_tree' panicked at
crates\wcore-sandbox\tests\live_integrity.rs:273:25:
runaway descendant exited before cancellation: Ok(SandboxOutput {
    exit_code: 1,
    stdout: [],
    stderr: [65, 99, 99, 101, 115, 115, 32, 105, 115, 32, 100, 101, 110, 105, 101, 100, 46, 13, 10],
    resource_limits: Enforced })
```

Those stderr bytes are ASCII for **`Access is denied.`**

Line 273 is the `panic!("runaway descendant exited before cancellation")` arm — the sandboxed
execution **returned before cancellation was ever applied**. The reap assertion
(`assert_eq!(final_len, settled, "descendant heartbeat advanced after execution future drop")`)
lives at line ~300 and is never reached.

### Three independent witnesses that the descendant never ran

| Witness | Reading | Meaning |
|---|---|---|
| `heartbeat.txt` in the work directory | **does not exist** | the heartbeat loop never executed once |
| sandbox result | `Ok(exit_code: 1)`, not a timeout or a kill | the command ran and refused, it did not linger |
| surviving `choice.exe` (the heartbeat loop's only sleep primitive) | **0 before, 0 after** | nothing survived, because nothing started |

### The non-vacuity discipline this leg required

The test's first statement is `if std::env::var("WAYLAND_SANDBOX_LIVE_WINDOWS").is_err() { return; }`,
so a plain `cargo test` **passes it without executing a line**. A vacuous control was run first
with the variable unset:

```
KR01_VACUOUS_RC=0        KR01_VACUOUS_SECONDS=0.82     <- what a vacuous green looks like
KR01_LIVE_RC=101         KR01_LIVE_SECONDS=0.53
```

**And the wall clock is what stopped this leg filing a false finding.** `rc=101` reads exactly
like "KR-01 reproduces". But the body cannot complete in 0.53 s — it sleeps 10 s waiting for
the heartbeat, then 2 s, then 2 s. The harness therefore refused to grade it and emitted
`KR01_VERDICT=UNREADABLE reason=live-run-too-fast-to-have-executed-the-body`, which is what
sent this investigation to the real cause instead of recording the headline.

## Why this is NOT a general sandbox failure, and NOT a load artifact

**AppContainer works on this box.** The full `live_integrity` suite, same binary, same session:

```
test live_cmd_builtin_runs_under_hardened_sandbox ... ok
test live_cmd_runs_when_allowlist_has_missing_path ... ok
test live_future_drop_reaps_descendant_job_tree ... FAILED
test live_lsa_dependent_tool_fails_under_hardened_sandbox ... ok
test live_runaway_command_is_bounded_by_timeout ... ok
test result: FAILED. 4 passed; 1 failed; 0 ignored; 0 measured; 0 filtered out; finished in 25.75s
```

**And the fs-ACL grant machinery works** — `live_fs_acl`, including
`granted_path_is_readable_then_revoked` and `ungranted_path_is_denied_in_sandbox`:

```
test result: ok. 12 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 16.37s
```

16.37 s of real work, so that green is not vacuous either.

**The discriminator.** All four passing `live_integrity` tests run `cmd.exe /c <builtin>` with
`cwd: None` and **no filesystem grants at all**. `live_future_drop_reaps_descendant_job_tree`
is the only one that writes a **script file to disk**, grants `fs_read_allow`/`fs_write_allow`
over its directory, sets `cwd: Some(work)`, and executes that file — and it places the
directory under **`%PUBLIC%` (`C:\Users\Public`)**, which no other live test uses.

The ACL on a leftover work directory shows no AppContainer identity at all:

```
DIR_ACL:
  BUILTIN\Administrators        FullControl
  CREATOR OWNER                 FullControl
  NT AUTHORITY\SYSTEM           FullControl
  NT AUTHORITY\INTERACTIVE      DeleteSubdirectoriesAndFiles, Modify, Synchronize
  NT AUTHORITY\SERVICE          DeleteSubdirectoriesAndFiles, Modify, Synchronize
  NT AUTHORITY\BATCH            DeleteSubdirectoriesAndFiles, Modify, Synchronize
```

An AppContainer token holds **none** of those identities, which is precisely `Access is
denied.` (This is the post-run state and the lease reverts its grant on release, so it does not
by itself prove the grant never applied — but combined with `live_fs_acl` passing 12/12, the
grant mechanism is demonstrably not broken in general.)

## Was it load?

No. It was run twice, under two different accounts, with load recorded both times:

| Run | Account | Competing load | Result |
|---|---|---|---|
| 1 | `SYSTEM` | 33 procs | `ExecFailed("AppContainer mutation-mutex DACL has an unexpected ACE count")` — a **SYSTEM-only** admission path, see below |
| 2 | `seand` (the interactive user) | 19 procs | `Access is denied.` — the result reported above |

Neither is the reap defect, and the failure is deterministic across both.

## Findings

| ID | Severity | Finding |
|---|---|---|
| **F-WR-01** | **HIGH** | `KR-01` does not reproduce as characterised. The carried red is **misattributed**: the test aborts on an access failure in its own setup and never evaluates descendant reaping. A HIGH row has been held against Criterion 2 on evidence that does not support it. The reap property is therefore **UNPROVEN — neither confirmed nor refuted — by this test**. It may take neither FIXED nor DISPROVED on this evidence. |
| **F-WR-02** | **HIGH** | `cargo test -p wcore-sandbox --test live_fs_acl` exits **0** and prints **`test result: ok`** while running **0 of 12** tests — all are `#[ignore]`d behind a native-acceptance gate and need `-- --ignored`. A reader, a CI step or a plan gate that runs the obvious command sees a green that proves nothing. This is the self-passing-gate class, on the suite that certifies the sandbox's filesystem boundary. |
| **F-WR-03** | **MEDIUM** | The `live_future_drop_reaps_descendant_job_tree` scenario is the **only** live test exercising execute-from-an-fs-granted-directory, and it places its work dir under `%PUBLIC%`, which no passing test uses. That path is consequently uncovered by any green test. |
| **F-WR-04** | **MEDIUM** | **~600 leaked `wcoresandbox-<pid>` AppContainer profiles** under `%LOCALAPPDATA%\Packages` on this box, plus **20 leaked `wcore-job-cancel-*` work directories** under `C:\Users\Public` (the work dir is removed only on the test's success path, so the count is a direct census of historical failures of this test). |
| **F-WR-05** | **LOW** | Running the sandbox as `SYSTEM` trips `validate_mutex_security` — `acquire()` always builds a **2-entry** DACL while the validator expects **1** when the caller's SID *is* the SYSTEM SID (`same_authority`). Fails closed with a message that reads like a platform limitation. Not the shipping configuration, so LOW, but it is the `KR-05` pattern and it cost this lane a run. |

## Independent evidence on what `KR-01` was *supposed* to be about

Criterion 2's actual subject matter is *the soak completes with no orphan process*. That was
measured directly in leg 1 of this lane, on the same host and the same candidate:

```
windows  census backend=windows-job-object  authoritative=True
         orphans_found=0   control_orphan_found=True
windows  orphan-census  green
```

A deliberately orphaned control process **was planted and FOUND**, so the census demonstrably
enumerates. Over 1,000 sessions at concurrency 4, **zero orphaned product processes survived**.
That is positive evidence on the property `KR-01` was standing in for — and it is stronger
evidence than the misattributed red it replaces, because it comes from a detector proven able
to see the thing it is looking for.

## What this leg did NOT establish

It did not prove descendants **are** reaped on future-drop. The scenario that would prove it
cannot currently run. `F-WR-01` is a correction to the attribution, not a clean bill of health,
and the honest state of the reap property under this specific scenario is **unproven**.
