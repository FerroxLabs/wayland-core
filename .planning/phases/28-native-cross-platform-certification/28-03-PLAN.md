<objective>
Run the 1,000-session and concurrent-child soak against the resolved candidate on every required OS family, and prove — with a positive control behind every observable — that no secret leaked, no process was orphaned, no resource grew without bound, and no quality or performance delta exceeded a band decided before the numbers were seen.

Purpose: Criterion 2 is four claims in one sentence, and three of them are provable only by evidence that a detector was working. A clean canary scan and an absent canary scanner produce identical output; so do a clean orphan census and an orphan census that never ran. This plan therefore builds each observable with a deliberate positive control and voids any run that misses it. The fourth claim, the quality and performance delta, has no defined threshold anywhere in the program, so the threshold is decided by cross-audit in advance rather than fitted to the result afterwards.
Output: a decided and dissent-recorded definition of an unacceptable delta; a soak harness exercising the candidate's resolved surfaces with concurrent children; and a per-family result stating how many sessions actually completed and giving Criterion 2 an honest verdict on each platform — including, if the carried Windows process-tree reap failure reproduces, a plainly stated NOT MET.
</objective>

<execution_rules>

**THE TWO AMENDED PHASE RULES — stated verbatim, and they bound this plan.**

- Findings at CRITICAL or HIGH must be fixed or disproved. MEDIUM and below are logged to BACKLOG and do not block execution.
- Execution begins when no CRITICAL or HIGH finding is open, or after 2 review rounds, whichever comes first. A third round is not permitted; it escalates to Sean.

**NON-NEGOTIABLE, stated verbatim.** A REPORTED RED IS WORTH FAR MORE THAN AN ENGINEERED GREEN — never weaken an assertion, `#[ignore]`, `#[allow]`, re-gate, delete a test, or raise a timeout to reach a gate.

**EVERY OBSERVABLE CARRIES A POSITIVE CONTROL, AND A MISSED CONTROL VOIDS THE RUN.** A canary scan that reports no leaks is accepted only if a deliberately planted control canary was DETECTED by that same scan in that same run on that same platform. An orphan census that reports no orphans is accepted only if a deliberately orphaned control process was FOUND. This is not belt-and-braces; it is the difference between measuring the product and measuring nothing. A run whose positive control was missed is VOID, not green, and its own miss is a finding.

**BANDS ARE DECIDED BEFORE THE NUMBERS ARE SEEN.** Task 1 completes and its bands are committed before task 3 runs. Widening a band after observing a result is the specific forgery this plan is most exposed to, and it is forbidden. If the measured drift exceeds the decided band, that is a finding — scored under the 28-01 rubric, re-scored against Phase 28's criteria under A1, and subject to A2 if it contradicts Criterion 2.

**ONE THOUSAND SESSIONS IS THE REQUIREMENT.** A family that cannot complete 1,000 in the available window records how many it completed and marks Criterion 2 NOT MET for that family with the shortfall named. It does not reduce the target, declare a smaller run representative, or extrapolate. This plan has no authority to redefine its own success condition.

**THIS PLAN REPAIRS NOTHING.** A defect the soak finds — including the carried Windows descendant-process-tree reap failure, which this plan expects to reproduce — is recorded with a Phase 28 severity and routed under the amended rules. Repairing it is not this plan's job and would corrupt the measurement, because a certifier that fixes what it measures is measuring itself.

**PROVE IT ON THE REAL PRODUCT.** The soak drives the shipped `wayland-core` binary, digest-bound to the candidate ledger on each host before the run starts. In-process assertions are permitted as an additional leg and are never sufficient alone.

**THE SESSIONS EXERCISE THE CANDIDATE'S RESOLVED SURFACES.** Read them from `evidence/28-01/candidate.json` at execution time. Do NOT write a session workload against features named in any planning document — phases 24 through 27 were mid-flight when this plan was written and their landed surfaces were unknown by construction. A soak whose workload was guessed certifies the guess.

**ENVIRONMENT.**
- **Windows OpenSSH kills session children on disconnect.** A 1,000-session soak started directly over ssh dies the instant the call returns. Register a scheduled task, log to a file, poll for an exit marker. The ssh call returning is not evidence.
- **The two Windows runners are ONE physical box.** A soak is the longest-running thing this phase does, so nothing else may run on that box while it does. Serialize; every recorded row names its single quiet run. A red produced under concurrent load is not a recordable red.
- **hetzner-dsm:** worktree `/root/wayland-p28`, cargo at `/root/.cargo/bin/cargo`, targeted `-p` builds only. Check `df -h /root` BEFORE a soak — this one writes a long series and a thousand sessions of artifacts, and a filled disk on that box took sshd down for hours previously. Treat a connection timeout as load to back off from.
- **macOS:** the certification Mac runs the CI arm64 binary and no cargo beyond `cargo fmt --all -- --check`.
- Mac `grep` and `ls` are rtk-proxied and SILENTLY DROP LINES — always `/usr/bin/grep`, `-F` for literals, `/usr/bin/git` for git.

**THE CROSS-AUDIT PANEL, AND ITS VOTE-LOSS TRAPS.** Task 1 is decided by the four-way panel, not escalated. Each member silently drops its vote if invoked wrong, which is the same defect class as a self-passing gate: `gemini` returns nothing without `--skip-trust`; `kimi` bullet-prefixes and indents, so an anchored position regex loses its vote and extraction must be unanchored; `codex` repeats its final block, so take the LAST match; and kimi needs its absolute path because a Bash-tool shell predates the PATH export. A one-word probe passes despite all three — probe with a real question. Add one internal adversarial pass arguing AGAINST the emerging consensus. Take the majority, or the minority when it carries stronger evidence, and say which and why.

**TERMINATION CRITERION FOR THIS PLAN (hard).** This plan decides ONE set of bands, authors ONE soak harness, and executes it ONCE per OS family. It terminates in exactly one of four states, and in all four it writes its SUMMARY and stops:
1. **Complete.** Bands decided, harness built, soak run on every required family with positive controls caught, and every observable has a verdict. Write the SUMMARY and stop.
2. **Complete with stated exceptions.** As above, but one or more observables are RED, or a family completed fewer than 1,000 sessions, or a family could not be run at all. State exactly which, the shortfall, and what evidence would close it. Criterion 2 is marked NOT MET for that family. This is a PASSING state for the plan and an HONEST one for the phase.
3. **Terminated — an observable cannot be measured.** A positive control cannot be made to fire on some platform, meaning that observable has no working detector there. STOP for that observable, record precisely what fires and what does not, and escalate. Do NOT report a clean result from a detector you could not prove works.
4. **Escalated — the harness cannot be made to work.** Bounded at TWO repair iterations of the HARNESS, where an iteration is one edit-build-run cycle on real hardware. After the second, STOP, record every remaining failure with its output, and escalate.
Under no circumstances does this plan repair a production defect, modify any production file under `crates/*/src` outside `wcore-eval-scenarios`, modify or delete an existing test, raise a timeout, reduce the session target, widen a band after measurement, sign a receipt, or create a fifth Phase 28 plan.

**THE PHASE PLAN CAP.** Phase 28 is capped at FOUR plans. This is the third.

  <options>
    <option id="drift-within-run">
      <name>Drift within the run — a late session window compared against an early window on the same host in the same run (RECOMMENDED starting position)</name>
      <pros>Measures the thing Criterion 2 actually asks: whether a thousand sessions degrade the product. Self-normalising, so it does not encode the hardware it was authored on and stays meaningful across three OS families with very different performance. Needs no historical baseline, which the program does not have per-platform. Detects a leak or a slow degradation, which is the failure mode a soak exists to find.</pros>
      <cons>Blind to a product that is uniformly slow or wrong from session 1, since a flat-but-bad run shows no drift. Sensitive to window size and placement, which must be fixed in advance rather than chosen to taste. A noisy host can manufacture drift that is not the product's.</cons>
    </option>
    <option id="absolute-bands">
      <name>Absolute per-metric ceilings, fixed in advance per platform</name>
      <pros>Catches a uniformly bad run, which drift cannot. Simple to state, simple to check, and a reader of the receipt can see what was promised. Independent of window choice.</pros>
      <cons>Encodes the hardware it was written on; the Windows box, the Linux server and the arm64 Mac differ enough that one set of numbers is either too loose somewhere or unreachable somewhere. Every ceiling would be invented today with no measurement behind it, which is exactly the kind of number that later gets widened.</cons>
    </option>
    <option id="drift-plus-floor">
      <name>Drift within the run as the primary gate, plus a small set of absolute sanity floors that catch a uniformly broken run</name>
      <pros>Covers both failure modes — degradation over the run and a run that was bad throughout. The floors can be deliberately loose, since their job is to catch catastrophe rather than to grade performance, which removes the pressure to widen them.</pros>
      <cons>Two mechanisms to specify, implement and explain. A loose floor invites the argument that it is decorative. More surface for a later reader to misread which gate actually fired.</cons>
    </option>
    <option id="defer-to-observation">
      <name>Run the soak first, characterise the distribution, then set bands from what was observed</name>
      <pros>Bands would be grounded in real measurement on real hardware instead of invented in advance, and would not be arbitrary.</pros>
      <cons>It is the forgery this plan is most exposed to, wearing a methodology's clothes: a threshold derived from the run it is meant to judge cannot fail that run. It makes Criterion 2 unfalsifiable for this candidate. If characterisation is genuinely needed, it must come from a separate, earlier, explicitly-labelled characterisation run that is not the certification soak.</cons>
