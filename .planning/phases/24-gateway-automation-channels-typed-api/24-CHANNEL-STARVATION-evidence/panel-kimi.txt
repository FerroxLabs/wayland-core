• PANEL_PRECEDENCE=service
  PANEL_MECHANISM=yield
  PANEL_RANK=gateway>cron>session

  **Justification.**

  1. **service.** The service is the thing the user *installed to be always-on*; a hand-run session is by definition transient. When first-come wins, the common failure is the worst possible one: the user starts a session, the service goes silent for hours or days (sessions get left open in tmux, VS Code terminals, SSH), and the user concludes the service is broken. Precedence must encode intent, not arrival order. The correct invariant is "if the service is alive, it polls" — everything else is a degraded mode.

  2. **yield.** Preemption without preemption primitives means the holder must yield voluntarily, and an advisory claim file is the right shape: it is strictly a hint, never an authority. Because flock remains the single arbiter of ownership, the failure modes all degrade *downward* to today's behavior rather than sideways into corruption — missing/stale/corrupt claim → holder keeps polling → first-come. That is the critical property: you add an optimization layer on top of a correct floor, you never lower the floor. A few implementation constraints that follow from the mechanism's safety argument:

     - **Claim before contend.** Every process writes/refreshes its own claim file (role rank + pid + timestamp) *before* attempting the lease, and refreshes it on a heartbeat. Non-owners re-attempt the lease on a timer; the owner polls the claim directory on the same cadence it polls channels (or a divisor of it) and yields only to a claim that is (a) strictly higher rank, (b) timestamp-fresh within a bounded window, (c) from a live pid. Checking pid-liveness plus freshness bounds the stale-file hazard.
     - **Yield = drop lease, stop polling, become a re-attempting non-owner.** No special states; the yielder just joins the same acquisition loop as everyone else, which keeps the state machine at two states (polling owner / contending non-owner).
     - The session should print the loud warning already built — ideally upgraded to name the outranking role ("polling held by gateway pid 1234").

  3. **gateway > cron > session.** Gateway is the installed always-on unit — highest. Cron-daemon is long-lived and scheduled but not user-facing, so it outranks an interactive session: if a cron daemon is running and no gateway exists, it is the closest thing to always-on infrastructure and should poll rather than defer to a terminal the user may close in five minutes — at which point cron reacquires. Session is explicitly the transient, foreground override and ranks last. Note this preserves the good property of the current behavior: a session started while the service is *down* polls immediately, and cedes when the service comes up.

  **Strongest argument against (1).** Preemption introduces a new failure class that first-come cannot have: *churn*. With first-come, the worst case is a static, silent misallocation that at least never loses a message mid-stream — one poller, stable, deliveries contiguous. With yield, a buggy or flapping claim layer could cause ownership to move repeatedly, and each handoff is a window where a destructive read races a lease transition; getUpdates offset state / IMAP UID state must survive the handoff or you get redelivery or gaps. You are trading a benign, observable misallocation for a mechanism that, if wrong, corrupts delivery continuity. The mitigation is that claim-layer bugs can only ever produce first-come behavior or extra handoffs, never dual pollers — but that floor argument deserves honest weight, and it's why the yield path needs a live handoff test (session polls, service starts, ownership visibly moves, no duplicate/lost delivery across the transition), not just unit tests.

  **Does strict inequality alone prevent oscillation?** Yes, given two conditions that are cheap to enforce. Strict inequality removes the symmetric case: with equal ranks neither side yields, so a pair of same-role processes can never chase each other. Asymmetric ranks can't ping-pong either, because only the higher rank ever triggers a yield and the lower rank has no action that displaces the higher — the transition graph is acyclic. The two conditions: (a) ranks must be a *total* order with no ties across roles — per-role rank, not per-process — and (b) the loser, after yielding, must not immediately outbid via some timestamp or recency tiebreak (there must be none — rank is the only criterion). If you ever add a tiebreak (e.g. "older claim wins"), you reintroduce a cycle risk and must re-prove acyclicity. Optional belt-and-suspenders: a minimum-hold cooldown after any yield, which bounds churn rate even under a corrupt-claim bug.

  **Can a stale claim from a dead claimant wedge or flap the system?** No, if and only if the yield check requires liveness. A stale claim fails one of two gates: its timestamp is older than the freshness window, or its pid is dead (`kill(pid, 0)` / `OpenProcess`). Either failure → claim ignored → holder keeps polling. So a dead claimant's leftover file is inert. It cannot wedge because ignoring a claim always resolves to "current holder continues" — the safe direction. It cannot flap because a stale claim never triggers a yield in the first place. What bounds it concretely: freshness window on the claim heartbeat (e.g. 3× the claim refresh interval), pid-liveness check at evaluation time, and treating unreadable/corrupt claim files as absent. The residual edge is pid reuse: a dead claimant's pid recycled by an unrelated process. Timestamp freshness covers it — a reused pid's claim is still stale unless the new process is a wayland process actively refreshing it, in which case it *is* a live claimant and ranking it is correct. Writing claims as `<role>.<pid>.claim` under the same lock directory, and deleting your own claim on clean exit, keeps the directory self-cleaning but must not be load-bearing — the liveness gate is the actual defense.
