## wcore-cli library suite — AND AN INSTRUMENT TRAP WORTH RECORDING

    cargo test -p wcore-cli --lib
    OUTER_CARGO_RC=0
    test result: FAILED. 0 passed; 1 failed; 0 ignored; 0 measured; 0 filtered out
    test result: ok.  1897 passed; 0 failed; 1 ignored; 0 measured; 0 filtered out

The `FAILED` line is NOT this crate's result. `plugin::scaffold::tests::
plugin_test_propagates_a_failing_suite` (which PASSES) scaffolds a plugin crate
containing `fn always_fails() { panic!("deliberate") }` and runs a NESTED cargo
inside it to prove a failing scaffold propagates. That nested run's `failures:`
block, its `test result: FAILED` line and its `error: test failed, to rerun pass
--lib` all interleave into the outer stream.

So on this crate a matcher keyed on `^test result:` or on `FAILED` or on `^error`
reports a RED against a suite that passed — a false red manufactured by the
product's own test output. Established here by taking the outer process's exit
code directly (rc=0) and by reading the failing test's own name back
(`always_fails`, at `src/lib.rs:2:21` — a path that does not exist in this
workspace). Same family as LANE-BRIEF 3b: trust the count and the process, not a
grep over interleaved output.

The real result is 1897 passed / 0 failed / 1 ignored.
