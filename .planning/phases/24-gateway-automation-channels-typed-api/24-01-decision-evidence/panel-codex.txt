=== F24-01 TASK 3 DECISION: Which mechanism makes the Wayland Core gateway a persistent, operator-managed service on Windows? ===

--- CONTEXT ---
wayland-core is a Rust agent CLI. Phase 24 Success Criterion 1 requires native service
lifecycle (install / start / status / drain / restart / upgrade / rollback) on macOS, Linux
AND Windows. On macOS and Linux this is settled: per-user launchd agent and per-user systemd
unit templates already exist in the repository for the background scheduler and are directly
reusable for the gateway. Windows has NO equivalent. The current non-Unix spawn branch in
crates/wcore-cli/src/cron.rs sets NO creation flags; the Unix sibling calls process_group(0),
which is setsid.

Criterion 5 additionally requires a live setup-to-recovery journey on Windows in which the
platform's OWN service mechanism -- not the test script -- brings the runtime back after a
hard kill that allows no drain.

--- OPTIONS (verbatim from the plan; do not re-scope them) ---

win-service-scm: A real Windows service registered with the service control manager, with the
  gateway answering the service control handshake in-process.
  PROS: the platform's own answer to a persistent background runtime; starts before login;
  survives console close by construction; restarts under the platform's own recovery policy;
  inspectable with the tools a Windows operator already uses; the closest structural match to
  the launch agent and the systemd unit, so the three families stay one contract with one
  implementation each.
  CONS: registration needs elevation, which puts an administrator prompt in the install path;
  the process must answer the control handshake within the platform's timeout or the platform
  kills it, so the drain budget and the service stop timeout must be reconciled explicitly; it
  adds a platform service dependency to a crate that currently has none.

win-scheduled-task: A scheduled task registered to run at logon, with the gateway staying an
  ordinary detached process.
  PROS: no elevation in the ordinary case, so the install path stays a single non-privileged
  command; the closest analogue to the per-user launch agent and per-user systemd unit already
  in the repository, which keeps the three families symmetric in privilege as well as in shape;
  restart-on-failure is expressible in the task definition.
  CONS: it does not start before login, so a headless or unattended box behaves differently
  from the Unix families and that difference must be documented rather than discovered; task
  registration and query go through an external command-line tool, which is a weaker contract
  than a typed platform interface and needs its output parsed carefully.

win-detached-only: Fix only the detach flags and ship no Windows service integration this phase.
  PROS: smallest change; correcting the missing creation flags is a real defect fix that stands
  on its own regardless of which mechanism is chosen later; it unblocks every other Windows
  behaviour in this phase without committing to a registration model.
  CONS: the first Success Criterion says native service lifecycle, and a process that must be
  started by hand after every logon is not that; it leaves Windows visibly behind the other two
  families and pushes the gap into a later phase where it competes with certification work.

win-defer: Defer the Windows mechanism entirely and record the criterion as not closed on that
  platform.
  PROS: nothing is built on an unauthorized mechanism, and the gap is visible in the record
  rather than absorbed into an implementation detail.
  CONS: the phase cannot honestly claim its first or fifth Success Criterion, since both name
  Windows explicitly. The decision only moves, it does not go away.
