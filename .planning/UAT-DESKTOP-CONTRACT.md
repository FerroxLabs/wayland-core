# UAT — Desktop ↔ Core JSON stream protocol contract

Lane `uat-desktop-contract`. Branch `lane/uat-desktop-contract`, base integration
`e9bed1af`. Core side read at `e9bed1af`; Desktop side read at
`/Users/seandonahoe/dev/wayland` (READ-ONLY — nothing was written, staged or
committed there, and its test suite was not run).

Evidence: `.planning/evidence/uat-desktop-contract/`.

---

## Verdict

**Desktop and Core do NOT agree at contract regen #4.** The corpus being green
15/15 is true and is not evidence of agreement — Core validating its own golden
files says nothing about the host.

The headline number, from the **real binary** rather than from static files:
in an ordinary session, Core emitted 38 frames and **Desktop's decoder would
drop 27 of them (71%)**, including `execution_policy` and `workspace_policy` —
the two frames that describe the session's security posture, emitted
immediately after `ready`.

Separately and more seriously: **Desktop implements no part of the contract
negotiation mechanism.** The `contract` block that regeneration #4 exists to
produce — major/minor, generator, and the three digests — is written by Core
and read by nobody. Desktop's decoder cannot tell the golden `ready` from one
carrying `major: 2` and forged digests.

The protocol doc already predicted this. `docs/json-stream-protocol.md`
L1133-1140 states that whether the production Electron decoder honours the Host
Decoder Contract "is a **follow-up audit, not covered by W0**." This lane is
that audit. The answer is: it honours rules 1, 4 and 5, and violates rules 2
and 3.

### Scope judgement — and what I did NOT do

I did not attempt GUI-level UAT and I am not going to dress up what I did as
one. I never launched Electron, never rendered a frame, never clicked anything,
and never executed a Desktop handler body. Driving that GUI headlessly against
a live engine was not achievable in this lane, and a weaker test relabelled
"Desktop UAT" would have been worth less than saying so.

What I did instead, at the seam:

1. Drove the **real** `wayland-core 0.12.25` binary on hetzner over the real
   JSON stream protocol and captured its real 38-frame output. This is what
   breaks the corpus's circularity — the golden files are generated by the same
   code that validates them, so they cannot disagree with themselves.
2. Ran that real output, and all 52 golden fixtures, through **Desktop's real
   `protocol.ts` types** using the **real TypeScript compiler** (5.9.3, from
   Desktop's own `node_modules`, used read-only).
3. Derived Desktop's runtime dispatch from its real `index.ts` switch, and
   swept the whole 1866-file Desktop source tree for every event name.

§"Coverage limits" below states precisely what that leaves unproven.

## 1. What I could prove they agree on

- **Every command Desktop can send, Core accepts.** Desktop's `WCoreCommand`
  union declares 11 types; all 11 are present in Core's `ProtocolCommand`
  (24 tags). Set G (Desktop sends / Core rejects) = **0**.
- **Desktop has no dead decoder arms.** All 33 event types Desktop handles are
  really emitted by Core. Set D = **0**.
- **No dead fixtures.** All 52 corpus event types exist in Core's enum.
  Set B = **0**.
- **`set_mode: "yolo"` really is accepted.** Desktop's declared union omits the
  canonical `"force"` that `ready.capabilities.modes` advertises, but
  `SessionMode` carries `#[serde(alias = "yolo")]`, so Desktop's value parses.
  This agreement is real but incidental — see finding L-2.
- **Optional-field back-compat holds.** Core's `ToolApprove.answer`,
  `AddMcpServer.allow_local`, `SetConfig.compaction` and
  `ApprovalResume.modifications` are all `#[serde(default)]`, so Desktop
  omitting them is safe.
- **The brief's premise held.** `events/ready.json` `contract` really does
  declare major 1, minor 10, generator `wcore-desktop-contract-gen/11`.
  Verified by reading the file, not taken from the brief.

## 2. Where they disagree

### 2.1 Event types Core emits that Desktop drops — 26 of 59

Core `ProtocolEvent` = 62 variants → **59 distinct wire tags** (three
`Correlated*` variants share a tag by `#[serde(rename)]`). Desktop handles
**33**. Unhandled:

```
anvil_receipt                    provider_attempt
anvil_receipt_invalidated        provider_failover_receipt
budget_grant_result              provider_failure
capability_activation            provider_retry
compact_offload                  runtime_diagnostics_snapshot
execution_policy                 runtime_diagnostics_unavailable
goal_control_refused             session_recovery_replay
goal_snapshot                    session_recovery_snapshot
goal_transition                  session_recovery_unavailable
mcp_removal_result               turn_recovery_lifecycle
mid_flight_monitor_decision      unknown_tool_effect_resolved
workflow_finished                workflow_node_event
workflow_started                 workspace_policy
```

Measured absence, not assumed: a whole-tree sweep of **1866** Desktop
`.ts/.tsx/.js` files (node_modules and vendor excluded) returns **0 files** for
each of these names. Controls in the same invocation: `browser_policy_denied`
3 files, `host_send_message_request` 4 files, sentinel 0 files.

### 2.2 What that costs in a real session — the live measurement

`wayland-core --json-stream --session-id abcdef123456`, 21 commands on stdin,
`WLRC=0`, 38 frames, 10 distinct types.

| | frames |
|---|---|
| `capability_activation` — dropped | 24 |
| `execution_policy` — dropped | 1 |
| `workspace_policy` — dropped | 1 |
| `budget_grant_result` — dropped | 1 |
| **total dropped** | **27 / 38 = 71%** |
| handled (`info`×5, `pong`×2, `ready`, `config_changed`, `error`, `approval_resume`) | 11 |

Control: live types absent from Core's enum = **[]**, confirming the enum
extraction is complete.

`capability_activation` is the single most frequent event in an ordinary
session and is in **neither** Desktop's decoder **nor** the corpus.
`execution_policy` carries `posture`, `approvals`, `sandbox: "required"`;
`workspace_policy` carries the trust level, sandbox backend and writable roots.
Both are dropped.

### 2.3 Fields Core sends on types Desktop DOES handle — 16 fields, 5 types

The type-name differential misses these entirely; only the field diff finds
them. `tsc` reports just the first excess property per object, so it
understates — an independent extractor was written and **cross-validated by
reproducing all 5 of tsc's findings (control 5/5 PASS)** before its extra
findings were trusted.

| event | fields Core sends that Desktop's types do not declare |
|---|---|
| `ready` | `contract`, `execution_policy`, + `memory_enabled`, `online_evolution`, `user_model_backend` in `capabilities` |
| `config_changed` | `memory_enabled`, `online_evolution`, `user_model_backend` |
| `stream_end` | `agent_run_id`, `usage_delta`, + `active_window_percent` in `usage` |
| `sub_agent_event` | `child_run_id`, `child_sequence`, `event_id`, `run_id` |
| `session_cost` | `priced` in `per_turn` |

These are **not** Host Decoder Contract rule-4 violations: JS ignores unknown
properties, so Desktop tolerates them at runtime as required. The cost is that
Desktop cannot *use* data Core is already sending — notably the four
`sub_agent_event` correlation fields, which are exactly what the
`CorrelatedSubAgentEvent` variant exists to provide, and `stream_end.usage_delta`.

### 2.4 Corpus gaps — the corpus is not a complete picture of Core either

- **7 event types Core emits are absent from the corpus**:
  `capability_activation`, `compact_offload`, `mid_flight_monitor_decision`,
  `provider_attempt`, `provider_failure`, `provider_retry`, `workspace_policy`.
  Two of those (`capability_activation`, `workspace_policy`) are emitted in
  **every** live session — 25 of my 38 frames.
- **1 command absent**: `grant_workspace_capability`.

This is a statement about coverage, not a request to regenerate. **I did not
run `wcore-contract generate` and am not asking for it here** — flagged for the
orchestrator to route.

### 2.5 Command direction

Core accepts 24 command types; Desktop sends 11. Nothing Desktop sends is
rejected. The 13 Core accepts that Desktop never sends include the entire
durable-goal surface (`goal_open`/`declare_task`/`advance`/`cancel`/`resync`),
recovery (`session_resync`, `resume_turn`, `resolve_interrupted_approval`,
`resolve_unknown_tool_effect`), `continue_with_budget`,
`get_runtime_diagnostics` and `remove_mcp_server` — the send-side mirror of the
unhandled receive-side families.

Live command-surface behaviour worth recording:
- `set_mode` with **both** `"force"` and `"yolo"` was **refused** —
  *"an auto-approving mode (auto_edit/force) requires a local-operator opt-in
  (launch with --force or WAYLAND_ALLOW_WIRE_FORCE=1)"*. The refusal arrives as
  an `info` frame, not an `error`, so a host cannot distinguish it from chatter
  without string-matching.
- `add_mcp_server` after session start → `error` *"only allowed before first
  Message"*. Desktop's type exposes no such ordering constraint.

## 3. Adversarial fixtures — were they rejected for the STATED reason?

### Core's reference observer: YES, proven in both directions

`cargo test -p wcore-protocol --test desktop_contract_adversarial` →
**17 passed; 0 failed; 0 ignored; 0 filtered out** (count read back, not
inferred from exit status). Corpus 15/15 and `host_decoder_contract` 31/31,
both also `0 ignored; 0 filtered out`.

The tests assert **exact typed error equality**, not mere rejection:

| fixture | asserted outcome |
|---|---|
| `version-mismatch.jsonl` | `Err(UnsupportedContractMajor { actual: 2 })` |
| `schema-mismatch.jsonl` | `Err(SchemaDigestMismatch)` |
| `fixture-mismatch.jsonl` | `Err(FixtureDigestMismatch)` |
| `unknown-critical.jsonl` | `Err(UnknownCriticalEvent { event_type: "future_authority" })` |
| `unknown-criticality.jsonl` | `Err(UnknownCriticality { event_type: "future_unclassified" })` |
| `unknown-noncritical.jsonl` | `Ok(DroppedUnknownNonCritical { .. })` |

Each mismatch fixture differs from golden `ready` in exactly **one** field
(`major` 1→2; `schema_digest`→all-`f`; `fixture_digest`→all-`f`), so the
rejection cannot be incidental to some other difference.

**Falsification (proving the gate can fail, not only pass).** In my own hetzner
worktree at `e9bed1af` I flipped `unknown-critical.jsonl` from `critical:true`
to `critical:false` and re-ran:

```
test negotiated_host_rejects_unknown_critical_and_unclassified_events ... FAILED
  left:  Ok(DroppedUnknownNonCritical { event_type: "future_authority" })
  right: Err(UnknownCriticalEvent   { event_type: "future_authority" })
test result: FAILED. 16 passed; 1 failed; 0 ignored; 0 filtered out
```

The verdict depends on precisely the field under test. Restored with
`git checkout -- <one path>`; tree clean (`porcelain_lines=0`); 17/17 green again.

### Desktop: NO — and it has no rejection path to reject with

Desktop cannot be fed these fixtures and observed to reject, because there is
no code that could. Concretely:

- The three `ready` mismatch fixtures are **indistinguishable from golden** to
  Desktop. Compiled against Desktop's real `WCoreEvent`, the golden `ready` and
  all three poisoned variants produce the *identical* diagnostic at the
  *identical* column — the `contract` block is neither in Desktop's type nor
  read by its handler (`case 'ready'` stores only `session_id` and
  `capabilities`).
- `unknown-critical` and `unknown-criticality` reach `default:` at index.ts
  L1152, are logged `console.warn(... " - dropping")`, and are dropped —
  where the contract requires rejection.
- `unknown-noncritical` is dropped, which is correct, but **by coincidence**:
  Desktop drops it for the same reason it drops the other two, not because it
  read `critical:false`.

Desktop reads the `critical` field **nowhere**: non-comment occurrences of
`critical` under `app/src/process/agent/wcore/` = **0** (the 4 matches are all
prose in comments; control `msg_id` = 72 files tree-wide).

## 4. Does `docs/json-stream-protocol.md` match the code?

**Mostly, with three real divergences.**

1. **§4.1 documents an error response Core does not send.** The doc states that
   malformed JSON or an unknown command type yields
   `{"type":"error","error":{"code":"protocol_error",...}}`. I sent five such
   commands live (`zzz_unknown_command_type`, a `tool_approve` missing its
   required `call_id`, `not json at all`, `[1,2,3]`, `{"no_type_field":true}`).
   Core emitted **zero** `protocol_error` frames. Controls: known-positive
   `engine_error` = 1 in the same capture, sentinel = 0, and the pings on
   either side of the malformed block were **both** answered, proving the
   reader consumed them and survived. The fail-closed *safety* behaviour is
   correct and separately tested
   (`malformed_and_unknown_commands_never_deserialize_for_dispatch`); it is the
   documented *feedback* that is absent. A host that sends a malformed frame
   gets silence.

2. **Desktop's own comments misstate the contract they cite.** `protocol.ts`
   L13-14 and `index.ts` L1140-1142 both say the Host Decoder Contract requires
   hosts to "drop unknown variants silently" — and L1141 cites the section by
   name. That section (L1164-1166) says the opposite: *"Drop it only when the
   event explicitly carries `"critical": false`. Reject `"critical": true`, a
   missing classification, or a non-boolean classification. Unknown criticality
   is critical; hosts must not guess."* The code faithfully implements the
   comment, and the comment is wrong. This is the direct cause of finding H-1.
   (The likely origin is real: `host_decoder_contract.rs` — which the doc calls
   *legacy* additive decoding at L1186 — does contain
   `host_drops_unknown_event_type_silently`. Two decoder generations exist and
   Desktop implements the older one.)

3. **Coverage.** 44 of 59 event tags and 16 of 24 command tags appear in the
   doc. Undocumented events include `workflow_*`, `goal_*`,
   `runtime_diagnostics_*`, `mcp_failed`, `tool_panicked`,
   `plugin_registration_failed`, `provider_failover_receipt`. Query: a tag
   counts as documented if it appears backticked or as a `"type": "<tag>"` JSON
   sample. Controls: `ready`/`text_delta` True, `zzz_fake` False.

A fourth, minor: `commands.rs` L373-379 carries a **stale CRIT annotation**
asserting that Desktop's `WCoreCommand` union "is missing" the `approval_resume`
arm and that HITL tools "hang indefinitely" as a result. `protocol.ts` L324 has
that arm. The gap it describes is closed; the comment still claims it is open.

## 5. Findings

| # | Sev | Finding |
|---|---|---|
| H-1 | HIGH | Desktop violates Host Decoder Contract **rule 3**: it never reads `critical`, so it silently drops unknown events marked `critical:true` and unknown events with no classification, where the contract requires rejection. This is the mechanism designed to fail closed when Core ships ahead of the host — and Core is currently 26 event types ahead. |
| H-2 | HIGH | Desktop violates Host Decoder Contract **rule 2**: no contract negotiation of any kind. `fixture_digest`, `schema_digest`, `source_inputs_digest`, `major` — 0 occurrences tree-wide (control `capabilities` = 91 files). A `major: 2` `ready` with forged digests is accepted exactly like the golden one. Contract regen #4's central artifact is unread by its only consumer. |
| H-3 | HIGH | 26 of Core's 59 event types are unhandled; **27 of 38 real frames (71%) dropped** in a live session, including `execution_policy` and `workspace_policy` (security posture) at session start. |
| M-1 | MED | 16 fields across 5 handled event types are undeclared by Desktop, incl. all four `sub_agent_event` correlation fields and `stream_end.usage_delta`. Runtime-tolerated; the data is unusable. |
| M-2 | MED | Doc §4.1 documents a `protocol_error` response Core never emits (0/5 malformed commands, controls green). |
| M-3 | MED | Corpus omits 7 event types Core emits + 1 command; 2 of the 7 appear in every live session. Flagged, not regenerated. |
| L-1 | LOW | `error.msg_id` is `skip_serializing_if` on the wire but declared required in Desktop's type. Runtime-safe — the handler uses `?? this.activeMsgId ?? ''` — so this is a type-accuracy defect only. |
| L-2 | LOW | Desktop's `set_mode` union omits the canonical `"force"` that `ready.capabilities.modes` advertises; it works only via `#[serde(alias="yolo")]`. Both values are refused over the wire anyway without `WAYLAND_ALLOW_WIRE_FORCE=1`, and the refusal arrives as `info`, not `error`. |
| L-3 | LOW | Stale CRIT comment at `commands.rs` L373-379 describing an app-side `approval_resume` gap that is closed. |
| L-4 | LOW | Desktop's malformed-line handler `console.error`s per line with no rate limiting; the contract asks for rate-limited log-or-count. It also classifies a valid-JSON line with a missing/non-string `type` as "unknown event type" rather than malformed, collapsing a distinction rule 3 requires. |

H-1 and H-2 are Desktop-side fixes; nothing in this lane's repo changes.

## 6. Coverage limits — what is still unproven

**A skip is not a pass, so these are counted, not glossed.**

- **GUI-level UAT: 0 cells run.** No Electron launch, no render, no user
  interaction, no IPC-to-renderer path. Everything downstream of
  `onStreamEvent` — whether a handled event actually reaches the UI and
  displays correctly — is untested here. A real GUI UAT would still need to
  cover: that the 33 handled types render; that `approval_required` produces a
  usable approval card and its resume round-trips; that `tool_request` →
  `tool_running` → `tool_result` sequences render in order; that
  `host_send_message_request` is fulfilled by a real outbound channel; and that
  a mid-turn `error` terminalizes the turn in the renderer.
- **Handler bodies were read, not executed.** I proved which types reach a
  handler and which are dropped. I did not prove a handler does the right thing
  with the event it receives.
- **Live coverage is 10 of 59 event types.** With no provider credential no
  model turn ran, so `stream_start`, `text_delta`, `thinking`, the whole
  `tool_*` family, `stream_end`, `approval_required` and `suspend` were **not
  observed on the live wire**. Their analysis is static (Core enum + corpus +
  Desktop switch) and inherits the corpus's circularity. 49 types unobserved.
- **Desktop's test suite was not run** — that needs a build in a read-only tree.
- **The `error.msg_id` runtime-safety claim is by code reading**, not by
  executing Desktop's handler.
- The 26-type gap is stated at type level. I did not assess, per type, how bad
  dropping it is in product terms; `execution_policy`, `workspace_policy` and
  the `*_policy_denied`-adjacent families are the ones I would look at first.
