# 4/5. REMOVED 2026-07-31 -- FIXED, and proved fixed in BOTH directions.
#    The two entries read:
#      wcore-cli::harness_regression r011_channels_auto_register_logs
#      wcore-cli::harness_regression r012_honcho_fallback_on_no_key
#    They were TWO REGRESSION DETECTORS BLINDED BY LOG SILENCING: both asserted
#    on stderr, and observed stderr carried only the config-permission warning.
#
#    DIAGNOSIS -- measured on the shipped binary, not inferred from the diff.
#    The events never stopped firing; #147 moved the sink and the tests were not
#    moved with it. The eval harness spawns every engine through
#    `ChildEnvironment::apply_tokio`, which calls `env_clear()` and rebuilds the
#    environment from a fixed allowlist that does NOT contain RUST_LOG. So a
#    harness child always boots with RUST_LOG unset however the test process is
#    configured -- the old tests' `set_var("RUST_LOG", "info")` was a no-op, and
#    their failure text ("RUST_LOG did not propagate") was pointing at the right
#    fact for the wrong reason. With RUST_LOG unset, #147's subscriber tees the
#    whole INFO record into $WAYLAND_HOME/logs/wayland-core.log and admits only
#    ERROR to stderr. Probed directly, two arms, same binary:
#      RUST_LOG unset -> both lines in the log file, neither on stderr
#      RUST_LOG=info  -> both lines on stderr, no log file written
#
#    FIX. Both tests now read that record through the existing artifact
#    assertion (`Assertion::FileContains` against
#    <workdir>/.wayland-core/logs/wayland-core.log -- tempenv points
#    WAYLAND_HOME there, so it is an ordinary workdir-relative artifact), via
#    `run_with_binary_in_environment` with a test-owned TempEnv so the evidence
#    outlives the run. The needles were NARROWED, not widened:
#      R-011 "channel_manager.start_all() complete"
#      R-012 "user-model: using local backend"
#    The old R-012 list contained the bare substring "honcho", which also
#    matches the OPPOSITE branch ("auto-selecting honcho user-model backend").
#    R-012's ready-event layer was also hardened from `if let` to a hard assert;
#    it had never once executed, because the credential it relied on came from
#    `seed_json_stream_env`, which writes `[provider.<name>]` while the schema

# 6. REMOVED 2026-07-31 -- FIXED, in the same commit, measured in BOTH
#    directions. This entry read:
#      wcore-cli::portability_hostile_corpus hostile_refused_restore_leaves_an_occupied_target_byte_identical
#    and recorded, correctly, that a REFUSED restore changed the occupied
#    target's digest from 3044f265... to d50b29ed... . Its DIAGNOSIS — "the
#    refusal path has already written to the user's file", "data loss" — was
#    wrong, and is corrected here rather than quietly dropped, because the next
#    reader will find this line before they find the fix.
#
#    What the refusal actually left behind, measured against the real binary by
#    diffing the target tree rather than by reading the message:
#        + logs/                    (directory)
#        + logs/wayland-core.log    (0 bytes)
#    and nothing else. config.toml and keep.txt were byte-identical; no user
#    content was touched, so no data was lost. The writer was not the restore
#    path, which is why the restore path "looked careful": `main` opens
#    $WAYLAND_HOME/logs/wayland-core.log BEFORE dispatching the subcommand, and
#    $WAYLAND_HOME is the very directory `backup restore --home` was being asked
#    to decline. Every offline subcommand writes zero log bytes, so the file was
#    always empty — it existed only because `open` created it.
#
#    The same eager creation was hiding a defect that IS severe, found while
#    measuring this one and closed by the same change: `backup restore
#    <archive> --home $WAYLAND_HOME` into a genuinely EMPTY home was refused
#    with "the target already holds state ... choose an empty target", because
#    dir_holds_state saw the logs/ directory this same process had created
#    microseconds earlier. Restoring your own backup into your own home — the
#    reason the feature exists — was unreachable. Control: the identical
#    restore into a target that is NOT the process's $WAYLAND_HOME succeeded.
#
#    Fix (issue #932, which stays OPEN): RotatingLog binds its path with a
#    read-only probe and materialises the directory and file with the FIRST
#    RECORD. A run with nothing to say leaves nothing behind.
#
