## SR-29-0 — Do not change what `body_sha256` means (a request to NOT act)

**File:** `crates/wcore-eval-scenarios/src/receipt.rs` — `fn body_digest` (line 949) and
`EvidenceReceiptV1.body_sha256` (line 44).

Phase 29 stores `receipt_body_sha256` inside a **signed** release manifest
(`ReleaseManifestBodyV1.certification` → `CertificationBindingV1.receipt_body_sha256`).

**What breaks if this changes:** every previously signed release manifest silently begins
referring to a different object while its signature continues to verify. That is the worst
available failure mode because it is invisible. If the digest must change, bump
`RECEIPT_SCHEMA_VERSION` in the same commit (see SR-29-5).

`behavior_sha256` is NOT consumed by Phase 29 and may evolve freely.

## SR-29-1 (R28-A) — Add a packaged-artifact list to `ReceiptBodyV1`

**File:** `crates/wcore-eval-scenarios/src/receipt.rs`.

**Exact insertion point:** inside `pub struct ReceiptBodyV1` (begins line 60), as a new field.
Placing it immediately after `pub identity: IdentityEvidenceV1,` (line 62) keeps identity facts
together; any position is acceptable provided SR-29-5 is honoured.

**Exact lines to add:**

```rust
    /// Every distributed archive this certification covers, bound by digest.
    /// `identity.binary_sha256` is the EXTRACTED binary; these are the objects
    /// users actually download and that Sigstore attests.
    pub packaged_artifacts: Vec<PackagedArtifactEvidenceV1>,
```

plus a new struct alongside the other evidence structs:

```rust
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, Eq)]
pub struct PackagedArtifactEvidenceV1 {
    pub name: String,
    pub sha256: String,
    pub byte_length: u64,
    pub kind: String,
}
```

Phase 29's `PackagedArtifactV1` in `src/release_integrity.rs` already has this exact shape, so
the two join by digest with no adapter.

**What breaks if omitted:** measured at base, **nothing in the tree binds the attested archive
to the certified binary** — `actions/attest-build-provenance@v4` covers
`artifacts/wayland-core-*.{tar.gz,zip}` while `identity.binary_sha256` covers the extracted
binary, and a grep for `archive_sha256|archive_digest|packaged_artifact` across the updater,
`receipt.rs` and `receipt_policy.rs` returns zero. Without this field a release manifest cannot
honestly claim the certified candidate is the artifact users download, so Phase 29 must carry
`certification` as permanently `Unavailable` — which, by the release ledger's own rule, makes
**release acceptance structurally unreachable**. (Census **F29-CEN-10**, HIGH.)

## SR-29-2 (R28-B) — Add retained-log digests

**File:** `crates/wcore-eval-scenarios/src/receipt.rs`, `pub struct ReceiptBodyV1`.

**Exact lines to add:**

```rust
    /// Digest per retained evidence log, so evidence that outlives the runner
    /// is BOUND rather than referenced.
    pub retained_logs: Vec<RetainedLogEvidenceV1>,
```

with `RetainedLogEvidenceV1 { name: String, sha256: String, byte_length: u64 }`.

**What breaks if omitted:** evidence referenced by URL or run id is mutable and expirable. A
manifest binding a reference rather than a digest cannot detect that the log was replaced or
garbage-collected, so the audit trail degrades silently instead of failing closed.

## SR-29-3 (R28-C) — Add an explicit skipped-case policy

**File:** `crates/wcore-eval-scenarios/src/receipt.rs`, `pub struct ReceiptBodyV1`.

**Exact lines to add:**

```rust
    /// Cases deliberately not run, each with a reason code and the authority
    /// that permitted it. Absent from `results` is NOT the same as skipped.
    pub skipped_cases: Vec<SkippedCaseEvidenceV1>,
```

with `SkippedCaseEvidenceV1 { cell_id: String, reason_code: String, authorized_by: String }`.

**What breaks if omitted:** F28-04 forbids skipping a critical case, but today `required_cells`
plus `results` implies coverage and carries **no skip vocabulary at all**. A shrunken
`required_cells` with a complete `results` set is byte-indistinguishable from full coverage, so
a silent omission reads as a pass. Phase 29 cannot gate on something it cannot see.

## SR-29-4 (R28-D) — Add an environment digest

**File:** `crates/wcore-eval-scenarios/src/receipt.rs`, `pub struct TargetEvidenceV1`
(begins line 100) — the natural home, since it already carries `os`, `architecture` and
`sandbox_backend`.

**Exact lines to add:**

```rust
    /// Digest over the toolchain version, runner image and environment
    /// allowlist under which this certification ran.
    pub environment_sha256: String,
```

**What breaks if omitted:** F28-03 names environment, and the only environment facts available
today are `sandbox_backend` and `policy.effective_policy_sha256` — neither identifies the
toolchain or the runner image. This is not hypothetical: the release path builds
`aarch64-unknown-linux-gnu` using `cross` installed from **unpinned git HEAD**
(`.github/workflows/release.yml:136`, census **F29-CEN-06**, HIGH), and three jobs in
`nightly-windows-soak.yml` install `dtolnay/rust-toolchain@stable` instead of the pinned 1.95.0
(**F29-CEN-01b**, MEDIUM). Two receipts differing only by toolchain are currently
indistinguishable, so a certification run under a drifted toolchain is accepted as equivalent to
one run under the pin — and reproducibility claims become unfalsifiable for the same reason.

## SR-29-5 (R28-F) — Bump the schema version on any body change, or keep the digests neutral

**File:** `crates/wcore-eval-scenarios/src/receipt.rs` line 22 —
`pub const RECEIPT_SCHEMA_VERSION: u32 = 1;`

If SR-29-1 through SR-29-4 land (any of them), increment this to `2` **in the same commit**.

**What breaks if omitted:** Phase 29 pins `receipt_schema_version` inside the signed
certification binding and **fails closed on a version it does not know**. An unversioned body
extension changes `body_sha256` for identical evidence, so a manifest signed before the change
stops matching the receipt it was minted against — and surfaces at release time as an
indistinguishable digest mismatch rather than an actionable version error.

Phase 29 will accept version `2` once Phase 28 confirms which of SR-29-1..4 landed.

## What Phase 29 is NOT asking for

- **No change to `AuthorityClaimV1`.** The `Ci { key_id, signature_base64 }` shape is exactly
  right and Phase 29 consumes it as-is.
- **No change to the signature domain** `b"wayland.eval.receipt.v1\0"`. Phase 29's manifest and
  every state record carry their **own** separators precisely so that receipt.rs's does not have
  to move. Phase 29's contract suite asserts, in both directions, that a receipt signature
  cannot verify as a manifest signature and vice versa.
- **No relaxation of `validate_ci_provenance`.** Its rule that all five `VerificationPolicy`
  fields must be populated before CI authority is granted is correct fail-closed behaviour, and
  Phase 29 depends on it. Phase 29's own suite pins that rule as an assertion so a future
  loosening is visible.
- **No change to `receipt_policy.rs` or `bin/wayland-receipt.rs`.** Phase 29 mirrored their
  idioms (`SecretBytes`, wipe-on-drop, seed-from-stdin) into its own binary rather than
  extending theirs.

change silently.

## SR-29-6 — `.cargo/audit.toml`'s quick-xml exception rests on a falsified "sole path"

**Owner:** whoever owns `.cargo/audit.toml`, `.github/osv-scanner.toml` and
`crates/wcore-tools/`. **Severity: HIGH.** **Finding id: F29-02-H1.**

Wiring `deny.toml` for the first time (F29-CEN-04) surfaced this. `.cargo/audit.toml` line 54
silences `RUSTSEC-2026-0194` and `RUSTSEC-2026-0195` (quick-xml DoS pair, patched only in
>= 0.41.0), and `.github/osv-scanner.toml` carries the same disposition. The written
justification states:

> Parent trace (**sole path**): quick-xml 0.39.4 <- plist 1.9.0 <- syntect 5.3.0 <- wcore-cli.
> Threat model — **UNREACHABLE**: syntect is used only by the TUI diff widget ... reading
> syntect's EMBEDDED binary dumps. No user-supplied ... XML parsing anywhere in the workspace.

Measured on the real graph at `2fd771d2`, that is wrong in a way that matters:

| Consumer path | In the recorded justification? |
|---|---|
| quick-xml 0.39.4 <- plist <- syntect <- wcore-cli | yes |
| quick-xml 0.39.4 <- **wcore-tools** (direct dep, docx/pptx OOXML) | **no** |
| quick-xml 0.31.0 <- **calamine 0.26.1 <- wcore-tools** (xlsx) | **no** |

`crates/wcore-tools/src/doc_tool.rs` is an agent tool whose entire purpose is reading
**user-supplied** docx/pptx/xlsx. calamine 0.26.1 contains **25 `.attributes()` call sites**
(including `xlsx/cells_reader.rs`) and **zero `with_checks(false)`**, so RUSTSEC-2026-0194's
vulnerable default duplicate-attribute check is active on attacker-supplied spreadsheets.

**Disposition, stated precisely:**
- **RUSTSEC-2026-0195 (NsReader): the UNREACHABLE claim holds.** `NsReader` appears zero times
  in calamine and zero times in the workspace.
- **RUSTSEC-2026-0194 (quadratic attribute check): the UNREACHABLE claim is falsified.**

The HIGH attaches to the **control failure**, not the exploitability. The underlying impact is a
local CPU DoS in a CLI process (~6s per 80k-attribute tag by the advisory's own table), with no
data loss and no privilege escalation — MEDIUM in isolation. But a security exception was
granted, documented and renewed across two gating scanners on a dependency trace that omits the
reachable consumer, and every other suppression rides on that same process.

**NOT PROVEN HERE:** no malicious `.xlsx` was crafted and no CPU cost was measured end to end.
This is a static reachability argument from the real dependency graph and the real crate
sources. **Substitution point:** a PoC document driven through the `doc_tool` surface, by
whoever owns `crates/wcore-tools`.

**Asked for:** correct the trace and the threat model in both disposition files; then either
re-justify 0194 on the true graph, bound the attribute count at the `doc_tool` boundary, or
take the fix at source when `calamine`/`plist` release against quick-xml >= 0.41. Tracking
issue `FerroxLabs/wayland-core#142` already exists and should be updated rather than duplicated.

**Cross-audit:** codex 5.6 HIGH, kimi K3 HIGH, gemini 3.1 Pro MEDIUM (2–1). Gemini's dissent is
recorded rather than dropped: it argues severity must track actual risk — a local DoS requiring
the user to open a hostile document — and that the procedural flaw belongs in backlog. That is a
coherent position; the majority view, which this lane adopted, is that an exception process able
to certify a false threat model must be corrected before the phase closes.
