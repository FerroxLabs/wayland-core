### B — containment proven instead of asserted (`5ca243b8`)

Two defects, landed together because either alone is worse than neither:

* **No reachable pass state.** On Darwin `kill(-pgid, SIGKILL)` returns
  **EPERM**, not ESRCH, when the group's only member is the unreaped anchor
  zombie — which is exactly the state the success path deliberately creates via
  `waitid(WNOWAIT)`. `kill()` tolerated only ESRCH, so *every clean shutdown
  failed its own cleanup*.
* **No reachable fail state.** On the same backend `terminate()` set
  `cleanup_complete = true` and skipped verification, and
  `finish_cleanup` for `Backend::ProcessGroup` returned `Ok(())`. Containment
  was recorded "verified" by a function that measured nothing.

Both now share `wcore_types::process_group_census`, which **enumerates** the
group. `kill(-pgid, 0)` cannot be used — measured, it returns EPERM for *both*
"everything is dead" and "something survived that I may not signal".

Order is load-bearing: the proof runs **before** `reap_child`, because the
unreaped leader is the only thing pinning the numeric PGID.
`pgid_anchor_released` then stops `Drop`/`kill_tree` from ever signalling an id
the kernel may have recycled.

**Ablations (macOS), and note they kill *different* tests:**

| ablation | anchor-corpse test | live-member test |
|---|---|---|
| remove the EPERM tolerance | **RED** | green |
| blind the census to always-`Live(0)` | green | **RED** |

Neither half can be removed without something going red. That is the property
the last handoff demanded and it is now on record.

## 4. THE PLATFORM FACTS, MEASURED (do not re-derive these)

One C probe, `cc`-compiled, seconds to run — no cargo:

```text
getpgid(unreaped zombie)                    -> -1  ESRCH
proc_pidinfo(PROC_PIDTBSDINFO, zombie)      -> -1  ESRCH
kill(-pgid, 0)      group = corpse only     -> -1  EPERM   <- NOT discriminating
kill(-pgid, SIGKILL) group = corpse only    -> -1  EPERM
```

## 6. THE ONE THING THAT NEEDS SEAN'S EYES — `075b541b`

**This is a deliberate change of security semantics, not a bug fix.**

`MacProcessGroupAuthority::attach` could not establish containment on macOS for
*any* workload whose root finishes quickly — `git config` is the one that
surfaced it. Deterministic. It reds delegated dispatch outright plus six tests.

The post-attach check was `root.still_matches() && getpgid(root) == root`.
Per §4, **both conjuncts become unsatisfiable the instant the root exits**, and
the root routinely exits inside the socketpair+fork window.

The anchor is now the live **sentinel**, not the root — which is what
`signal_group` already relied on. A root that is a *corpse* is accepted; a root
that was *replaced* is still refused (identity recheck is now three-valued:
Same / Corpse / Recycled / Unreadable).

**The test `root_exit_during_group_attachment_fails_closed` asserted the old
rule and now asserts the opposite.** I did not do that quietly — it is called
out in the commit body and here.

Safety rests on: a pgid cannot be recycled while a live process sits in it, and
`setpgid` into a vanished group returns EPERM (measured, §4), so the sentinel's
successful join — already required *before* the post-check — proves the group
exists. A tripwire test
(`joining_a_vanished_process_group_is_refused_by_the_kernel`) fails loudly if
Apple ever changes that.

**This change was NOT verified locally** (no cargo on the Mac). CI Lint and
macOS native suites are green on it; the full macOS test leg had not reported at
handoff time. A 4-way cross-audit was commissioned specifically to attack it.
