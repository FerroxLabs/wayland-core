# Known-failing allowlist — the NAMED set a test run's failures are compared
# against. FerroxLabs/wayland-core#367.
#
# ── WHY THIS FILE EXISTS ───────────────────────────────────────────────────
#
# `8d6add71 RED ARM (throwaway, never merge)` reached `integ/f13` and survived
# three more commits. It was not hidden: a full workspace run reported it every
# single time. What it reported was `1 failed`, this repository is known to
# carry a standing failure, and `1 failed` was read as `the known 1 failed`.
# It was a different test — the process-tree guard's own regression case — and
# what shipped was a spawned process tree that outlives its guard
# (FerroxLabs/wayland#1156, reintroduced).
#
# A COUNT CANNOT SEE THAT. Swap one failure for another and the count does not
# move. `.github/scripts/grade-failing-set.sh` compares the failing test
# IDENTITIES in every leg's JUnit against the SET named here, and fails when
# they differ — including when they differ at the same count, which is the only
# case the old reading got wrong.
#
# ── WHAT A LINE HERE MEANS ─────────────────────────────────────────────────
#
# NOT "this test is allowed to fail forever". A line means "this failure is
# known, someone owns it, and the debt has a date on it". Every entry expires,
# and an expired entry fails the gate exactly as an unlisted failure does.
#
# It also means the run is RED-BY-POLICY-AND-GREEN-BY-EXCEPTION: the gate still
# names the test on every run as a warning. If the test starts PASSING, the gate
# goes red for a STALE entry and the remedy is to delete the line — an allowlist
# that outlives its failure is a hole the next unexpected failure fits through.
#
# ── FORMAT ─────────────────────────────────────────────────────────────────
#
#   <YYYY-MM-DD expiry>  <binary-id>::<test-name>  <gh#NNNN>  <reason...>
#
# Identical to .config/flaky-allowlist.txt, deliberately: one shape to learn,
# one validator to trust. Whitespace-separated; the reason is the rest of the
# line and is MANDATORY. The key is the JUnit `classname` and `name` joined by
# `::`, which is exactly what nextest prints on its FAIL line. A malformed line
# FAILS the gate — an allowlist nobody can parse is an allowlist that silently
# allows everything.
#
# This file is NOT .config/flaky-allowlist.txt. That one governs
# `<flakyFailure>` — a test that failed and was RETRIED INTO A PASS. This one
# governs `<failure>` — a test that simply failed. The two never see the same
# element and must not be merged; a retried failure and a hard failure have
# different remedies.
#
# Check a local `--profile ci` run before pushing:  just failing-set-gate
#
# ── THE SET, TODAY: EMPTY ──────────────────────────────────────────────────
#
# NOT YET MEASURED ON THIS BRANCH — the file ships EMPTY, which is the
# fail-closed state, and this paragraph is replaced by the workspace run that
# settles it rather than by a guess. The "standing known failure" this repository
# talks about —
# `wcore-exec-backend::conformance_matrix::every_reference_backend_passes_the_same_harness_or_reports_why_it_did_not`
# — did not fail in that run, and it is deliberately NOT seeded here as a hedge:
# an entry for a test that passes is a STALE entry, the gate reds on it, and
# seeding one would be the same "the count looked right" reasoning in a new
# file. Add a line only when a run has actually named the failure.
#
# An empty list is the fail-closed state: every failing test is unexpected.
