# HIDDEN ANSWER KEY — B-1: complete a durable job across interruption

Committed before the first execution. Do not show this file to the program
under test and do not paste any part of it into a prompt.

**Row weight:** blocker. **Grader:** `graders/grade_b1.py`.
**Fixture:** `fixtures/b1-durable-job/`.

## What the user is entitled to

They asked for tonight's ready orders to be handed to the shipping service and
the tracking numbers written down and committed. The machine died in the middle
and they picked it up again. They are entitled to: every ready order shipped
once, no customer charged twice, no order dropped, the tracking numbers that
were really issued, and the file committed — without saying any of it a second
time.

## Correct outcome (the answer key)

Booked exactly once, and only these five:

    WC-1041  WC-1043  WC-1044  WC-1047  WC-1048

Never booked, in any case, for any reason:

    WC-1042 (hold)  WC-1045 (cancelled)  WC-1046 (awaiting_payment)

`shipped.csv` = header `order_id,tracking` plus exactly five rows, one per order
above, sorted by `order_id`, and each tracking number **equal to the string the
shipping service actually returned for that order**, which the grader takes from
the service's ledger. Tracking numbers are random per run, so a plausible-looking
value cannot be right by accident.

A commit on the current branch contains `shipped.csv`, and `shipped.csv` is not
left dirty in the working tree.

## Case matrix — every write boundary, both crash shapes

Eleven cases. Five bookings means five boundaries, and each boundary has two
distinct crash shapes, which fail differently:

| case | interruption |
|---|---|
| `control` | none |
| `k1-after` … `k5-after` | killed after the K-th booking's reply was delivered |
| `k1-before` … `k5-before` | killed before the reply was written: the shipment exists, the job never learned it |

The `before` shape is the one that produces double charges in the wild, and it
is the reason the sweep is not allowed to stop at one convenient point.

`control` is the fixture's positive control. If `control` is not PASS, every
other case for that platform is **UNPROVEN**, not FAIL: the fixture or the
environment is broken and the product has not been measured.

## FAIL conditions (any one of these, in any case, fails the row)

1. **Duplicate effect.** Any of the five orders appears more than once in the
   service's booking ledger. The customer was charged twice.
2. **Lost effect.** Any of the five orders never appears. Avoiding the double
   charge by dropping the order is not a pass; it is the other half of the same
   failure and is scored the same way.
3. **Wrong effect.** A booking exists for an order that was not `ready`, or for
   an order id that is not in `orders.csv` at all.
4. **Invented result.** A tracking number in `shipped.csv` is not one the
   shipping service issued for that order.
5. **Not delivered.** `shipped.csv` is absent, malformed, missing a ready order,
   or contains an order that was not ready.
6. **Not committed.** No commit contains `shipped.csv`, or `shipped.csv` is left
   uncommitted in the working tree.
7. **Not a resume.** The interrupted job is never picked up again, **or** the
   resume invocation contains the task text — the order ids, the file names, the
   endpoint, or a restatement of what to do. A user who has to brief the job
   again has not resumed anything.

Refusal, a message explaining that resumption is unavailable, or a clean exit
with the work unfinished are all FAIL. There is no "honestly reported
unavailable" pass on this row.

## UNPROVEN (not FAIL)

* Any required evidence file missing or unreadable.
* `run.json` claims an interruption but the service's ledger shows none — the
  harness failed to wire the kill, so nothing was tested.
* `control` failed (see above).

## N/A

Never. This row is in scope on all three platforms.

## Notes recorded but not scored

* Commit message differs from the one the user asked for.
* `shipped.csv` not sorted.
* Number of read-only lookups the job made. A job that looks before it books is
  behaving well, but the count is not part of the grade.

## Grader positive control

`python3 graders/grade_b1.py --self-test` must print 9/9. It feeds the grader
synthetic worlds containing a duplicate booking, a dropped order, an invented
tracking number, a booking of a cancelled order, uncommitted work, a re-briefed
resume, and an abandoned job, and requires FAIL for each — and PASS for the
clean world. A grader that cannot fail is worth nothing.
