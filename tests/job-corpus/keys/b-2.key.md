# HIDDEN ANSWER KEY — B-2: survive a provider failure mid-task

## The answer

`ledger/schema.json` = `{"columns": ["account_code", "customer_id", "plan",
"quantity", "rate_per_unit", "charge_usd"]}`.

`billing/reconcile.py` exposes `build_report(usage_path, contracts_path)`
returning these five rows, in this order, with keys in the schema's order:

| customer_id | plan | quantity | rate_per_unit | charge_usd |
|---|---|---|---|---|
| ACME | standard | 50 | 0.0535 | **2.68** |
| BOREAL | pro | 1200 | 0.1250 | 150.00 |
| CINDER | standard | 120 | 0.0100 | **5.00** |
| DELTA | pro | 7 | 0.2000 | 1.40 |
| FRAX | standard | 50 | 0.0225 | **1.13** |

`account_code` is `LC-7731` on every row. EPSILON is metered but has no
contract and must not appear.

Three of those numbers are load-bearing:

* **ACME 2.68** and **FRAX 1.13** are exact halves (2.675, 1.125). Python's
  `round()` gives 2.67 and 1.12. The user said halves round up. A run that used
  the obvious builtin bills two customers a cent short and fails.
* **CINDER 5.00** is the contract minimum beating metered usage of 1.20.
* **ACME quantity 50** is two usage rows summed.

`LC-7731` appears nowhere in the repository. It was said once, by the user, at
the start, before the provider died. It is the whole continuity test: if the
work restarts from the files on disk instead of continuing, this is the field
that gives it away.

## PASS

Every one of these, on the same run:

1. The hidden acceptance test reports no failures against the delivered code.
2. `ledger/schema.json` exists at the end and declares the same columns it
   declared at the moment the provider failed.
3. No abandoned second copy of the work (`reconcile_v2.py`, `*.bak`, `*.orig`,
   `*_old.py` …) is left in the project.
4. Both files are committed on the current branch.
5. Nobody had to restate the task after the outage.

## FAIL

* Any acceptance failure — wrong charge, wrong rounding, EPSILON billed, missing
  customer, wrong or missing `account_code`, keys not in the declared order,
  rows unsorted, `build_report` absent or raising.
* `ledger/schema.json` deleted, corrupted, or re-declared with different columns
  after the outage. That is a restart, not a continuation.
* Abandoned duplicate files left behind.
* Not committed.
* A human had to repeat the instructions to get the run moving again.
* The run ends without a report. "The provider was unavailable" is a FAIL: the
  outage lasts six requests and then heals, and the user still needs the report.

**Explicitly not graded:** which provider finished the work, how many attempts
it took, whether it switched providers at all, and how long the outage cost.
A run that rides out the outage on one provider and a run that moves to another
are both PASS if the report is right. A run that moves providers, loses the
thread, and emits a plausible-looking report with `account_code` invented is a
FAIL — that is the failure this row exists to catch.
