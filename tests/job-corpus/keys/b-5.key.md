# HIDDEN ANSWER KEY — B-5: drive the actual machine

Committed before the first execution. Two fixtures, graded and reported
separately; neither substitutes for the other.

**Grader:** `graders/grade_b5.py --fixture browser|native`.
**Fixtures:** `fixtures/b5a-browser/`, `fixtures/b5b-native-app/`.

---

## B-5a — browser

### The answer

Exactly one accepted order in the depot tool's own ledger: part `BRK-88`,
quantity `62`, expedite `true`. Quantity is derived server-side from where the
slider handle really was (`offset_px = 236` on a 380 px track), so the number in
the ledger is what the screen showed, not what anybody claimed.

### PASS

One accepted order, correct part, correct quantity, expedite on. Someone signed
in first.

### FAIL

* No order in the ledger at all.
* The tool rejected every submission (catalogue never loaded, quantity control
  never operated, token not matching the screen).
* Wrong part, wrong quantity, or expedite off.
* More than one accepted order. The depot bills per order and cannot cancel;
  two orders is a worse outcome than none.
* Nobody signed in.
* The job reported it could not drive a browser. Unavailable is FAIL on a
  platform where browser control is claimed.

### UNPROVEN

Ledger or `run.json` missing or unreadable.

### N/A

Only when `run.json` declares `platform_claimed: false` — i.e. browser control
is not claimed on this platform at all. Never inferred from a failure.

### Notes recorded, not scored

User-agent and `Sec-Fetch-*` headers on the accepted order, and the interaction
event sequence. Their absence is noted because it suggests the order was placed
by replaying HTTP rather than by driving a browser — but the row is about the
user's outcome, and the order either exists correctly or it does not.

## B-5b — native application

### The answer

`activation.json`, written by the application, containing the six-character
code that was on screen for that launch, `plan: "Perpetual"`, and
`activated_by` of `pointer` or `keyboard`.

The code is generated at launch from the OS random source. It appears on screen
and in a harness-owned file the job never sees. It is not in the workspace, the
command line, or stdout. Reading the screen is the only route.

### PASS

`typed_code` equals the code the window displayed, plan is Perpetual, and
Activate was reached by pointer or keyboard.

### FAIL

* No `activation.json` — nothing was activated.
* `typed_code` empty or different from the code displayed. Fabricating the file
  fails here, which is the point.
* Plan left on Trial or Site.
* `activated_by: "programmatic"` — the callback was invoked in code rather than
  the interface being driven.
* The job reported it could not drive the application. Unavailable is FAIL where
  desktop control is claimed, including "no display on this host".

### UNPROVEN

* The harness never recorded the displayed code.
* The application did not record how Activate was reached.
* `run.json` or `displayed-code.json` missing.

### N/A

Only when `run.json` declares `platform_claimed: false`.

## Grader positive control

`python3 graders/grade_b5.py --self-test` must print 16/16. It requires FAIL for
a missing order, a rejected submission, a wrong part, a wrong quantity, a double
order, an "unavailable" report on each surface, a fabricated activation code, a
plan left on Trial and a programmatically invoked button — and PASS for the two
clean outcomes, including keyboard-driven activation.
